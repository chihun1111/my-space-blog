# 말씨 개발 기록: AI의 답변을 끝까지 전달하고 저장하기

입력 보존과 재시도부터 모델 역할 분리, 답변 버전·작업 실행 권한까지. 말씨에서 AI 대화를 저장과 복구로 이어 간 개발 기록.

작성일: 2026-11-26

사용자가 답변을 고치는 동안 이전 요청의 결과가 도착하면 어떻게 해야 할까. 브라우저를 닫았다가 다시 열었을 때는 어디서 이어 가야 할까. 모델이 문장을 반환했지만 데이터베이스 저장은 실패했다면, 화면에 완료라고 표시해도 될까.

말씨에서 내가 다룬 문제는 이런 질문들과 맞닿아 있었다. [말씨](https://github.com/seonizz/HOP_Biohealth_AI-Challenge/blob/d134a006ba6098afa63ef1477f193375eca36b6f/README.md)는 HOP Biohealth AI Challenge에서 함께 만든 팀 프로젝트로, 어려움을 겪는 사람 곁의 가족이나 친구가 대화와 행동을 준비하도록 돕는 서비스다. 사용자가 원하는 도움과 상황을 설명하면 필요한 정보를 확인하고, 대화문과 행동 가이드를 카드로 제공한다.

나는 기존 화면에 PostgreSQL과 Gemma 모델 경로를 연결하고, 입력 보존·재시도·후속 대화·결과 저장을 개선했다. 이후에는 질문을 고르는 모델과 최종 카드를 만드는 모델을 나누고, 답변 수정과 서버 재시작에 대응하는 작업 처리를 반영했다. 이 글은 그중 **질문을 시작한 시점부터 올바른 결과를 저장할 때까지 대화 상태를 유지하는 과정**을 다룬다.

## 전송한 답변을 끝까지 책임지기

대화 화면에서는 사용자가 메시지를 보내면 자신의 말풍선이 바로 보이는 편이 자연스럽다. 그렇지만 화면에 표시됐다는 사실만으로 모델 처리와 저장까지 끝났다고 볼 수는 없다. 입력을 받는 단계, 모델의 결과를 검증하는 단계, 대화 상태에 반영하는 단계가 각각 있기 때문이다.

여기서 입력창을 비우는 동작과 제출한 원문을 보존하는 동작을 함께 생각해야 했다. 요청이 실패했을 때 같은 답변으로 재시도할 수 있어야 하고, 응답을 기다리는 동안 화면을 이동하더라도 작성 중인 내용과 이미 제출한 내용을 구분할 수 있어야 한다. 모델 응답이 확인되기 전에 다음 질문으로 넘어가면 화면과 서버가 서로 다른 대화를 진행하게 된다.

그래서 모델 처리 실패 뒤에도 제출한 내용을 다시 다룰 수 있도록 입력과 진행 상태를 보존하고, 중단된 요청 이후의 초안과 화면 이동을 보완했다. [입력 초안·이동 상태를 보존한 변경](https://github.com/seonizz/HOP_Biohealth_AI-Challenge/commit/3168a23409469021c772cf62204faae31baf33c1)은 이 흐름을 다룬다.

이때부터 대화 기능을 볼 때 확인하는 기준도 구체적이어야 했다. “답변이 보인다”에 이어, 어떤 질문의 답인지, 어떤 버전의 입력으로 처리했는지, 실패했을 때 어디에서 다시 시작할 수 있는지를 함께 확인하는 것이다.

## 목적만 받았는데 질문을 끝내지 않도록

질문 흐름에서는 사용자의 부담을 줄이면서도 결과에 필요한 맥락을 확보해야 했다. 질문은행의 문항을 모두 순서대로 묻는 방식은 한 답변에 여러 정보가 들어오는 상황을 잘 활용하지 못한다. 이미 원하는 도움과 실제 상황을 함께 설명했다면 같은 내용을 다시 물을 필요가 없다.

새 대화는 목적과 상황을 먼저 확인하고, 보통 2~4개 질문에서 필요한 정보를 얻는 방향으로 바꿨다. 질문 수는 설계 목표다. 네 개를 채우는 것이 완료 조건은 아니며, 모든 실제 모델 실행에서 그 수를 달성했다는 뜻도 아니다. 추가 질문의 기준은 **그 답을 알아야 사용자가 요청한 결과가 달라지는가**로 잡았다.

분리 모드의 질문 라우터는 다음 행동을 세 가지 중 하나로 반환한다. `existing`은 질문은행의 후보를 선택하고, `custom`은 후보로 확인하기 어려운 정보를 짧게 묻는다. 현재 답변으로 결과를 준비할 수 있으면 `finish`로 질문을 마친다. 질문을 선택할 때는 근거가 된 원문의 인용과 출처 ID, 질문이 필요한 이유도 함께 반환한다.

서버에서는 후보 문항과 원문 인용이 유효한지, 이미 발행한 문항과 등록된 확인 범위가 겹치지 않는지 검사한다. 의미가 비슷한 모든 재질문을 이 검사만으로 판별할 수는 없으므로, 질문의 필요성은 모델 지침과 검토 경로에서도 다룬다. 이 판단과 검증을 [질문 라우터](https://github.com/seonizz/HOP_Biohealth_AI-Challenge/blob/d134a006ba6098afa63ef1477f193375eca36b6f/app/src/split-question-router.js)에 모았다.

질문을 줄이면서 보완한 구체적인 경계 사례가 있다. 첫 답변이 **“상황을 정리하고 싶어요.”**인 경우다. 이 문장은 원하는 도움을 알려 주지만, 정리할 사건이나 상황은 아직 담고 있지 않다. 여기서 `finish`를 허용하면 모델이 무엇을 정리해야 하는지 모르는 상태로 결과 단계에 들어간다.

해당 선택형 답변이나 같은 문장의 자유 입력만 들어온 경우에는 상황 문항 `q3_03`을 먼저 보여 주도록 수정했다. 회귀 검사에는 두 입력 형태를 넣었다. 반대로 “상황을 정리하고 싶어요. 어제 친구와 말다툼했어요.”처럼 상황까지 포함한 입력은 이 강제 분기로 처리하지 않는지도 확인했다. 이 입력들은 [목적만 있는 입력의 조기 종료를 막는 수정](https://github.com/seonizz/HOP_Biohealth_AI-Challenge/commit/6bc95b2c46498aa51c28f4a8d1a851c76e1b0e00)에 넣은 합성 회귀 사례다.

## 질문과 최종 카드는 다른 작업으로 나누기

다음 질문 하나를 고르는 단계에는 최신 답변, 앞선 답변의 필요한 부분, 이미 물은 문항과 다음 후보가 필요하다. 최종 카드를 만드는 단계에는 전체 답변을 바탕으로 분석하고 내용을 생성·검토하는 과정이 필요하다. 두 단계의 입력과 책임을 분리했다.

관리자 설정에서는 대화 모델과 분석·카드 모델을 각각 선택할 수 있게 했다. 12B와 31B 프로필을 제공하고, 분리 모드에서는 전용 질문 라우터를 사용한다. 이 경로의 질문 모델 호출은 답변 제출당 최대 한 번이다. 최종 카드 생성과 검토는 그 호출 제한에 포함되는 작업이 아니라, 대화가 끝난 뒤 별도로 수행하는 단계다.

최종 생성은 암호화해 저장한 대화 원문을 읽는다. 질문 단계에 전달한 짧은 발췌만으로 전체 상황을 대신하지 않는다. 질문용 연결과 결과용 연결의 버전도 대화에 고정해, 관리자 설정이 바뀌었다고 진행 중인 대화의 처리 조건이 갑자기 달라지지 않게 했다.

또 하나 바꾼 것은 결과 생성의 수명이다. 대화가 결과를 만들 수 있는 상태가 되면 해당 답변 버전의 작업을 등록하고, 서버의 작업자가 처리한다. 브라우저의 결과 요청이 계속 연결돼 있어야만 생성이 이어지는 구조에서 벗어나기 위한 변경이다. 검토를 통과한 카드는 준비되는 순서대로 전달하고, 전체 결과와 기록은 같은 데이터베이스 트랜잭션으로 저장한다.

[질문과 최종 카드 모델을 분리한 변경](https://github.com/seonizz/HOP_Biohealth_AI-Challenge/commit/9e1d4f6ab4a86a9f6b194c3bf83538a803455ff2)에는 관리자 설정, API, 데이터베이스 마이그레이션, 질문 라우터와 결과 작업자를 함께 반영했다. 모델 크기를 나눈 효과는 실제 실행에서 확인해야 하지만, 각 단계가 어떤 입력을 읽고 언제 완료되는지는 코드에서 명확히 구분할 수 있게 됐다.

## 답변을 고쳤다면 이전 결과도 오래된 결과다

백그라운드 작업을 만들면 브라우저 연결과 생성 작업을 분리할 수 있다. 대신 답변 수정과 결과 저장 사이의 경합을 처리해야 한다. 요청을 취소하는 것만으로는 충분하지 않다. 취소 신호가 전달되기 전에 모델 응답이 돌아오거나, 다른 작업자가 이미 결과를 처리 중일 수 있기 때문이다.

아래는 이 문제를 설명하기 위한 가상의 순서다. 숫자는 답변 버전을 단순화한 것이다.

| 순서 | 일어난 일 | 서버가 지켜야 할 조건 |
| --- | --- | --- |
| 1 | 답변 7번 버전으로 작업 A 시작 | A는 7번 버전에 대한 결과만 저장할 수 있다. |
| 2 | 사용자가 답변을 수정해 8번 버전이 됨 | 7번 버전의 작업을 무효화한다. |
| 3 | 작업 A의 모델 응답이 뒤늦게 도착 | 성공한 응답이어도 현재 결과로 저장하지 않는다. |
| 4 | 8번 버전이 결과 생성 가능한 상태가 됨 | 유효한 새 작업으로 생성하고 저장한다. |

결과 작업은 대화 ID, 소유자, 답변 버전, 실행 토큰으로 식별한다. 작업 큐에는 이 식별 정보와 실행 상태를 두고, 답변과 카드 원문은 기존 암호화 저장소에 둔다. 답변 상태가 바뀌면 이전 작업을 지우고, 새 상태가 결과 생성 조건을 만족할 때 작업을 등록한다.

작업을 가져올 때는 PostgreSQL의 `FOR UPDATE SKIP LOCKED`로 이미 다른 작업자가 잡은 항목을 피한다. 가져온 작업에는 만료 시간이 있는 실행 권한을 부여하고 처리 중 주기적으로 갱신한다. 프로세스가 멈춰 갱신하지 못하면 권한이 만료된 작업을 다시 가져올 수 있다.

저장 직전에도 답변 버전과 실행 토큰, 권한의 유효 시간을 다시 검사한다. 재시작 뒤 새 작업자가 맡은 작업을 이전 작업자가 늦게 완료하더라도, 오래된 실행 권한으로 결과를 반영할 수 없도록 하는 장치다. 재실행이 가능한 구조인 만큼 **어떤 실행의 결과를 최종 상태에 반영해도 되는지**를 저장 단계에서 확인해야 한다. 이 처리는 [결과 작업자 코드](https://github.com/seonizz/HOP_Biohealth_AI-Challenge/blob/d134a006ba6098afa63ef1477f193375eca36b6f/app/src/split-result-jobs.js)에 들어 있다.

## 원문을 고치면 그 원문에서 나온 판단도 다시 보기

결과 작업만 답변 버전을 따라가면 충분한 것은 아니다. 개인화 질문도 앞선 답변을 근거로 만들어지므로, 그 답변이 수정되면 다시 판단해야 한다.

개인화 결정에는 원문 문항 ID, 수정번호, 인용과 그 구간을 연결했다. 서버는 현재 답변에 해당 인용이 실제로 있는지 대조한다. 사용자가 원문을 고치면 연결된 추가 질문과 답변을 연쇄적으로 무효화한다. 중간 질문만 무효화되고 그 질문에서 파생된 다음 답변은 남는 일이 없도록 처리해야 하는 부분이다.

질문 문구와 사용자 답변도 저장할 때 구분한다. 화면에 어떤 질문을 보여 줬는지는 대화 이력을 설명하지만, 그 질문에 들어 있는 전제를 사용자가 말한 사실로 저장할 수는 없다. 미응답이나 건너뛴 문항은 그 상태로 남기고, 결과를 완성하기 위해 답을 채우지 않는다. [개인화 질문의 저장·검증 계약](https://github.com/seonizz/HOP_Biohealth_AI-Challenge/blob/d134a006ba6098afa63ef1477f193375eca36b6f/app/docs/PERSONALIZED_QUESTIONS_2026-11-17.md)은 원문과 그 원문에서 나온 판단의 관계를 정리한 문서다.

## 질문·복구·저장을 각각 검증하기

검사에서도 여러 종류의 성공을 구분했다. 합성 모델 응답을 넣으면 오류나 늦은 완료를 원하는 시점에 발생시켜 저장과 복구를 검사할 수 있다. 실제 모델을 연결하면 질문 선택과 생성 결과를 볼 수 있지만, 실행 조건과 결과의 편차까지 함께 기록해야 한다.

질문셋을 JSON으로 작성해 앱의 문답과 모델 호출 경로를 재현하는 실행기도 추가했다. 앱의 입력 검증, 상태 전이, 모델 게이트웨이를 재사용하며, 현재 질문에 대응하는 답변이 준비되지 않았으면 `awaiting_input`으로 멈춘다. 테스트를 끝내기 위해 임의의 답을 만드는 흐름은 넣지 않았다.

보고서에는 기대값과 실제 결과, 오류, 호출 수와 실행 상태를 남긴다. 모델 설정 조회와 생성 요청을 나누고, 제공되지 않은 토큰 수는 미확인으로 둔다. [모델 테스트 실행기 규격](https://github.com/seonizz/HOP_Biohealth_AI-Challenge/blob/d134a006ba6098afa63ef1477f193375eca36b6f/ai/docs/MODEL_QUESTION_TESTS.md)에서 재현 방법과 검사 범위를 볼 수 있다.

11월 18일에는 로컬 12B로 합성 대화의 질문 경로를 실행했다. 결과 저장 쪽은 합성 결과 모델과 격리된 PostgreSQL을 연결해 부분 카드 전달, 브라우저 연결 종료 뒤 완료, 답변 수정에 따른 작업 무효화, 장애 재시도와 재시작 복구를 확인했다. 저장한 암호화 기록을 다시 조회했을 때 결과가 일치하는지도 검사했다. 실제 31B의 최종 생성·검토 시간과 카드 품질은 이 검증에 포함되지 않는다.

다음에는 같은 대화에서 질문 선택부터 실제 최종 모델의 생성·검토·저장까지 이어지는 결과를 확인하려고 한다. 목적만 받았을 때 필요한 상황을 묻는지, 이미 설명한 내용을 되묻지 않는지, 마지막 결과가 현재 답변의 버전으로 저장되는지를 함께 볼 것이다. 시간도 질문 응답, 카드 생성, 검토, 최종 저장으로 나누어 기록할 필요가 있다.

말씨를 만들며 내가 더 신경 쓰게 된 것은 사용자가 기다리는 동안에도 이어지는 대화의 상태다. 입력을 받았으면 실패 뒤에도 다시 사용할 수 있어야 하고, 답변이 바뀌었으면 그에 맞는 결과만 남아야 한다. 이 흐름이 유지돼야 모델의 출력도 사용자가 이어서 쓸 수 있는 서비스의 결과가 된다.
