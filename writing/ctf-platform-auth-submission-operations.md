# CTF 플랫폼을 만들며 배운 인증·제출·운영의 경계

Next.js·NestJS와 PostgreSQL을 중심으로 개인별 플래그, 인증, 제출 트랜잭션, 감사 기록과 Docker 운영 구조를 정리했습니다.

작성일: 2026-11-26

CTF 대회를 위한 웹 페이지를 만들고, 서버 구축부터 배포까지 직접 맡았다. 참가자가 문제를 열고 정답을 제출하는 화면뿐 아니라, 운영자가 진행 상황과 제출 내역을 확인하는 기능도 함께 구현했다. 이 경험을 통해 개발과 서버 운영은 같은 서비스의 서로 다른 면이라는 점을 구체적으로 다루게 됐다.

이 글은 그 개발 경험을 출발점으로, **2026년 11월 16일 보강된 공개 저장소의 현재 구조**를 정리한 기록이다. 앞서 만들고 배포했던 경험과 이후 보강한 구현은 구분한다. 아래 설명은 과거 운영 환경이 모두 이 구조였다는 뜻이 아니라, 현재 코드에서 확인할 수 있는 설계와 남아 있는 운영 과제를 다룬다. [코드 기준: c042607](https://github.com/chihun1111/CTF_KDU/tree/c042607b76563c51f99758901d120d92f2f6b8af)

## 문제 화면과 운영 플랫폼을 함께 설계하기

현재 플랫폼은 Next.js 프런트엔드, NestJS 백엔드, PostgreSQL, Redis, Nginx, 그리고 8개의 문제 서비스로 구성된다. TypeScript 모노레포 안에 화면과 API, 공통 설정, Drizzle 데이터베이스 스키마를 두고, Docker Compose로 실행 환경을 정의했다.

참가자는 로그인한 뒤 문제 목록에서 각 문제로 바로 이동한다. 찾은 플래그는 일부만 먼저 제출해 확인할 수 있고, 최종 완료에는 개인에게 발급된 8개의 플래그를 한 번에 제출한다. 운영자는 가입·제출·완료 현황과 문제 서비스 상태를 확인한다. 이 흐름에서 핵심은 “누가 요청했는가”, “어떤 문제의 자료인가”, “이번 제출로 무엇이 바뀌는가”를 서버가 일관되게 판단하는 것이다. [프로젝트 구성과 참가 흐름](https://github.com/chihun1111/CTF_KDU/blob/c042607b76563c51f99758901d120d92f2f6b8af/README.md)

## 서비스의 역할을 나누고 데이터에 닿는 경로를 좁히기

문제 서비스에는 학습을 위한 취약한 동작이 들어간다. 그래서 참가자 계정, 정답 검증, 관리자 기능을 담당하는 플랫폼과 문제 서비스 사이의 경계가 중요하다.

현재 Compose 구성에서는 Nginx만 호스트 포트를 공개한다. PostgreSQL과 Redis는 내부 데이터 네트워크에 있고, 문제 컨테이너에는 데이터베이스 비밀번호나 전체 플래그 암호화 키를 전달하지 않는다. 문제 서비스는 자기 번호에 해당하는 내부 서비스 토큰으로 백엔드에 필요한 정보를 요청한다.

| 영역 | 담당하는 일 | 접근 범위 |
| --- | --- | --- |
| Nginx | 화면·API·문제 경로로 요청 전달 | 외부 요청의 진입점 |
| 프런트엔드 | 참가자와 운영자의 화면 | 애플리케이션 네트워크 |
| 백엔드 | 인증·개인별 플래그·제출·운영 API | 애플리케이션·문제·데이터 네트워크 |
| 문제 서비스 | 각 문제의 화면과 실습 동작 | 문제 네트워크와 자기 서비스 토큰 |
| PostgreSQL·Redis | 영속 데이터와 접속 현황 캐시 | 내부 데이터 네트워크 |

여기서 정확히 구분할 점이 있다. 문제마다 컨테이너는 따로 있지만, 8개 문제 서비스는 같은 `ctf_challenges` 네트워크를 공유한다. 따라서 현재 구조를 문제 간 네트워크 통신까지 완전히 차단한 구성이라고 설명할 수는 없다. 컨테이너 분리, 데이터 네트워크 분리, 서비스 토큰의 권한 검증이 각각 어떤 범위를 담당하는지 나누어 보는 것이 맞다. [Docker Compose 구성](https://github.com/chihun1111/CTF_KDU/blob/c042607b76563c51f99758901d120d92f2f6b8af/infra/docker/docker-compose.yml)

Nginx는 외부의 `/internal/` 요청을 차단하고, 클라이언트가 보낸 사용자 식별·내부 서비스 관련 헤더를 제거한다. 프록시가 전달했다는 이유만으로 임의의 헤더를 신뢰하지 않도록 진입점에서 한 번 정리하는 것이다. `X-Forwarded-For`도 클라이언트의 값을 이어 붙이지 않고 직접 연결한 주소로 설정한다. 이 선택은 나중에 외부 TLS 프록시를 추가할 때 다시 검토해야 하는 운영 조건이 된다. [Nginx 설정](https://github.com/chihun1111/CTF_KDU/blob/c042607b76563c51f99758901d120d92f2f6b8af/infra/nginx/nginx.conf)

## 인증 정보를 저장할 때 목적부터 나누기

비밀번호, 세션 토큰, 플래그는 모두 민감한 값이지만 필요한 처리 방식은 다르다. 비밀번호는 일치 여부를 확인하면 되고, 세션 토큰은 활성 세션을 찾는 데 쓰며, 플래그는 정답 비교뿐 아니라 문제 서비스에 전달할 원문도 필요하다.

현재 구현은 이 차이를 저장 방식에 반영한다.

- **비밀번호:** 용도를 구분하는 접두 문자열을 붙여 SHA-256으로 전처리한 뒤 bcrypt로 저장한다. 해시에 버전 접두어를 남겨 기존 bcrypt 레코드와 구분한다.
- **세션 토큰:** 브라우저에는 임의 토큰을 발급하고, 서버에서는 HMAC으로 계산한 값으로 세션을 찾는다. 만료 시각과 폐기 여부를 함께 확인한다.
- **플래그:** 정답 비교용 HMAC과, 내부 서비스에 원문을 제공할 때 사용하는 암호문을 따로 보관한다. 암호화 함수는 AES-256-GCM을 사용하며 키 버전도 함께 기록한다.

비밀번호 전처리는 bcrypt에 넘기는 입력을 고정 길이로 만들어 긴 입력의 구분을 유지하려는 구현이다. 기존 bcrypt 해시는 별도 분기로 검증하므로, 과거 레코드의 입력 길이 제약까지 자동으로 해소되는 것은 아니다. 현재 가입·로그인 입력 정책도 영문과 숫자 8~128자로 제한되어 있다. 이 정책은 현재 프로젝트의 제약으로 기록하며, 모든 서비스에 그대로 적용할 권장안으로 보지는 않는다. [비밀번호 해시 구현](https://github.com/chihun1111/CTF_KDU/blob/c042607b76563c51f99758901d120d92f2f6b8af/apps/backend/src/auth/password-hash.service.ts) · [암호 처리](https://github.com/chihun1111/CTF_KDU/blob/c042607b76563c51f99758901d120d92f2f6b8af/apps/backend/src/crypto/crypto.service.ts) · [공통 암호 함수](https://github.com/chihun1111/CTF_KDU/blob/c042607b76563c51f99758901d120d92f2f6b8af/packages/config/src/index.ts)

세션 쿠키에는 `HttpOnly`, `Secure`, `SameSite=Lax`를 설정한다. 실제 사용자와 역할은 쿠키 안의 임의 값을 그대로 믿는 대신, 데이터베이스의 활성 세션과 사용자 레코드를 조회해 결정한다. 상태를 바꾸는 플랫폼 API에는 브라우저의 Origin과 Fetch Metadata를 확인하는 가드도 둔다. 다만 같은 출처 검사와 사용자 인증은 서로 다른 검증이다. 헤더가 없는 서버 간 요청에도 기존 인증·권한 검사가 필요하다. [세션 조회](https://github.com/chihun1111/CTF_KDU/blob/c042607b76563c51f99758901d120d92f2f6b8af/apps/backend/src/auth/session-auth-drizzle.store.ts) · [쿠키 설정](https://github.com/chihun1111/CTF_KDU/blob/c042607b76563c51f99758901d120d92f2f6b8af/apps/backend/src/auth/session-cookie.service.ts) · [Origin 가드](https://github.com/chihun1111/CTF_KDU/blob/c042607b76563c51f99758901d120d92f2f6b8af/apps/backend/src/auth/api-origin.guard.ts)

문제 서비스가 내부 API로 플래그를 요청할 때는 두 가지를 확인한다. 먼저 요청한 문제 번호에 맞는 서비스 토큰인지 검사하고, 이어 참가자의 세션이 유효한지 확인한다. 조회 대상 사용자는 이 세션에서 얻으며, 그 사용자와 해당 문제의 조합으로 플래그를 찾는다.

## 정답 판정과 제출 기록을 같은 작업으로 다루기

제출 API는 입력 형식과 허용된 플래그 항목을 검사한 뒤, 로그인한 사용자의 정답 해시를 조회한다. 제출한 값은 그 사용자의 플래그들과 비교하며, 같은 정답을 여러 칸에 넣어도 여러 문제의 정답으로 중복 계산하지 않도록 이미 맞춘 항목을 추적한다.

그다음 제출 요약, 문제별 결과, 감사 기록을 같은 데이터베이스 트랜잭션 안에 저장한다. 8개를 모두 맞춘 경우에는 완료 기록과 인증 화면용 토큰도 이 작업 안에서 생성한다. 정답 판정은 성공했지만 완료 기록이 없거나, 제출 내역과 감사 기록이 서로 어긋나는 상태를 줄이기 위해 함께 성공하거나 함께 실패해야 하는 범위를 정한 것이다. [제출 서비스](https://github.com/chihun1111/CTF_KDU/blob/c042607b76563c51f99758901d120d92f2f6b8af/apps/backend/src/submissions/final-submit.service.ts) · [트랜잭션 저장소](https://github.com/chihun1111/CTF_KDU/blob/c042607b76563c51f99758901d120d92f2f6b8af/apps/backend/src/submissions/final-submit-drizzle.store.ts)

부분 제출의 의미도 명확해야 한다. 현재 점수는 최근 제출의 결과이고, 여러 번에 나눠 맞춘 값이 자동으로 합쳐져 최종 완료가 되는 방식은 아니다. 한 번 완료한 사실은 별도 완료 테이블에 남는다. 따라서 운영 화면의 “최근 정답 수”와 “완료 여부”는 서로 다른 질문에 답하는 값이다. 완료 후 다른 조합을 제출했을 때도 이 두 값을 혼동하지 않아야 한다. [운영 조회의 최근 제출·완료 구분](https://github.com/chihun1111/CTF_KDU/blob/c042607b76563c51f99758901d120d92f2f6b8af/apps/backend/src/admin/admin-operations-drizzle.store.ts)

완료 인증 화면을 여는 토큰에는 5분 만료 시간을 둔다. 소비할 때는 사용자, 토큰 해시, 만료 여부, 미사용 상태를 확인하고, `consumedAt`이 아직 비어 있는 행만 갱신한다. 실제로 갱신된 행이 하나일 때만 인증 정보를 반환한다. 먼저 조회한 뒤 단순히 사용 처리하는 것에 그치지 않고, 갱신 조건에도 미사용 여부를 넣은 것이 동시 요청을 다루는 핵심이다.

여기서 “한 번”은 **해당 인증 토큰을 한 번 소비한다는 뜻**이다. 이후 8개 정답을 다시 제출하면 새 토큰이 발급될 수 있으므로, 계정이 평생 인증 화면을 딱 한 번만 볼 수 있다는 의미와는 다르다. [인증 토큰 소비 처리](https://github.com/chihun1111/CTF_KDU/blob/c042607b76563c51f99758901d120d92f2f6b8af/apps/backend/src/submissions/clear-certificate-drizzle.store.ts)

## 운영 화면에는 판단에 필요한 정보만 남기기

운영자에게 필요한 것은 참가자가 어디까지 진행했는지, 제출이 정상적으로 처리되는지, 특정 서비스가 응답하는지다. 현재 운영 목록은 참가자를 가명 참조로 표시하고 최근 정답 수, 제출 횟수, 완료 여부 등을 보여 준다. 관리자 계정의 연습 데이터는 참가자 통계에서 제외한다.

감사 로그도 데이터베이스의 JSON을 그대로 화면에 보내지 않는다. 동작별로 허용할 필드를 정하고, 허용된 기본 자료형만 꺼내 전달한다. 예를 들어 최종 제출 로그에는 정답 수와 제출 수, 완료 여부를 남기지만 제출한 플래그 원문을 넣지 않는다. 이 가명 참조는 운영상 노출을 줄이는 수단이지, 모든 데이터 연결 가능성을 없애는 완전한 익명화라는 의미는 아니다. [운영 서비스와 감사 메타데이터 처리](https://github.com/chihun1111/CTF_KDU/blob/c042607b76563c51f99758901d120d92f2f6b8af/apps/backend/src/admin/admin-operations.service.ts)

Redis의 역할도 구분했다. 세션 인증의 기준 데이터는 PostgreSQL에 있고, Redis는 최근 접속 현황을 계산하는 캐시로 사용한다. Redis를 사용할 수 없거나 캐시에서 유효한 수를 얻지 못하면, 데이터베이스에 남은 최근 세션 활동으로 접속 현황을 계산한다. 응답에는 집계 출처와 시간 범위도 포함한다. 표시되는 값은 최근 활동 기준의 **세션 수**이므로, 고유 참가자 수나 바로 그 순간 연결된 사람 수와 동일하다고 해석하지 않는다. [접속 현황과 DB 대체 경로](https://github.com/chihun1111/CTF_KDU/blob/c042607b76563c51f99758901d120d92f2f6b8af/apps/backend/src/presence/online-count.service.ts)

## 배포는 실행 명령 이후까지 이어진다

현재 운영 문서에는 설치와 빌드뿐 아니라 데이터베이스 초기화, 배포 전 점검, 사용자 흐름 확인, 백업·복원, 비밀값 교체가 포함되어 있다. 서버를 직접 다루면서 남겨야 할 기록도 이 순서와 닮아 있다. “켜졌다”는 사실 다음에, 데이터가 유지되는지와 문제가 생겼을 때 돌아갈 수 있는지를 확인해야 한다.

특히 다음 조건은 코드와 실제 운영 환경을 연결한다.

- **HTTPS와 프록시:** 세션 쿠키는 `Secure`인데 기본 Nginx 진입점은 HTTP다. 외부 서비스에는 TLS 구성이 필요하며, 프록시를 한 겹 더 둘 때는 실제 클라이언트 IP 처리와 속도 제한 기준을 함께 검토해야 한다.
- **데이터와 암호화 키:** 데이터베이스 백업만으로 복원이 끝나지 않는다. 암호화 키와 조회용 비밀값을 잃거나 임의로 바꾸면 기존 데이터 복호화와 해시 조회에 영향을 준다. 백업과 키 보관, 교체 절차는 함께 설계해야 한다.
- **파일 권한과 실행 사용자:** 비밀값 파일의 읽기 권한은 컨테이너 실행 사용자와 맞아야 한다. 현재 일부 서비스는 이 호환성을 위해 root 실행과 제한된 capability를 유지한다. 비특권 사용자 전환을 확대하려면 파일 소유권과 볼륨 권한부터 정리해야 한다.
- **리허설 데이터:** 사용자 흐름 검사 스크립트는 계정을 만들고, 일부는 운영자 권한이나 공개 힌트를 변경한다. 운영 데이터베이스에서 무심코 실행할 점검이 아니므로 별도 환경에서 수행하는 절차가 필요하다.

검증 문서에는 코드 테스트, 컨테이너를 띄운 통합 확인, 브라우저 확인의 범위가 따로 적혀 있다. 이 글을 위해 코드를 읽은 것과 새로운 서버에서 전체 리허설을 수행한 것은 구분한다. 여기서는 특정 동시 접속 규모나 가용성, 모든 공격에 대한 방어를 검증했다고 주장하지 않는다. [설치·운영·백업·비밀값 교체 가이드](https://github.com/chihun1111/CTF_KDU/blob/c042607b76563c51f99758901d120d92f2f6b8af/docs/operations.md)

## 다음 보강에서 확인할 것

현재 운영 계약은 백엔드와 각 문제 서비스를 단일 인스턴스로 실행하는 구성이다. 인증 속도 제한과 일부 문제 상태가 프로세스 메모리에 있으므로 복제본을 늘리면 공유 상태나 요청 배치 방식부터 다시 설계해야 한다. 컨테이너 수를 늘리는 작업만으로 확장이 끝나지 않는다.

비밀번호 재설정 화면, 암호화 키 이전 도구, 예상 참가자 수를 기준으로 한 부하 리허설도 별개의 과제다. 개인별 플래그와 데이터 경계를 마련한 것에 이어, 실제 규모에서 자원이 어떻게 사용되고 장애 시 무엇이 유지되는지 확인할 필요가 있다. 현재 운영 문서가 이 범위를 남겨 두고 있다는 점까지 함께 기록하고 싶다. [현재 운영 경계](https://github.com/chihun1111/CTF_KDU/blob/c042607b76563c51f99758901d120d92f2f6b8af/docs/operations.md#6-현재-운영-경계)

CTF 플랫폼을 통해 남길 수 있었던 경험은 화면 구현, 인증과 데이터 모델링, 배포 설정, 운영자의 확인 흐름까지 하나의 서비스로 연결해 본 일이다. 앞으로도 프로젝트를 소개할 때 사용한 기술 이름과 함께, 그 기술을 어디에 두었고 어떤 상태를 지키기 위해 그렇게 구성했는지 기록하려 한다.
