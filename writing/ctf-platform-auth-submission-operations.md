# CTF 사이트를 만들면서 정리한 것들

CTF 사이트를 만들면서 정답과 제출 기록을 어떻게 관리했는지, 서버에 올릴 때 챙길 것은 무엇이었는지 정리했어요.

작성일: 2026-11-26

CTF 대회용 사이트를 직접 만들어 봤어요. 문제 페이지에 로그인, 정답 제출, 관리자 화면을 붙이고 서버에 올리는 것까지 해봤어요. 이번 글에는 그 과정에서 정했던 것들을 적어 보려고 해요.

현재 화면은 Next.js, API는 NestJS로 만들었고, PostgreSQL과 Redis를 함께 써요. 문제는 8개이고 Docker Compose로 서비스들을 띄우는 구성이에요. 아래 내용에는 처음 배포한 뒤 11월에 보강한 부분도 포함되어 있어요.

## 문제는 따로 띄우고, 접속은 한곳에서

CTF에는 일부러 취약하게 만든 문제도 있어요. 문제를 풀다가 계정이나 다른 참가자의 데이터까지 건드릴 수 있게 되면 곤란하니, 문제 서비스와 운영 데이터를 나눠 두었어요.

각 문제는 별도 컨테이너에서 실행해요. 외부 요청은 Nginx로 받은 다음 화면, API, 문제 주소에 맞게 전달하고, PostgreSQL과 Redis는 내부 네트워크에 두었어요. 문제 컨테이너에는 DB 비밀번호를 주지 않고, 필요한 자료를 백엔드에 요청하도록 했어요.

현재 8개 문제 컨테이너는 같은 문제용 네트워크를 쓰고 있어요. 지금은 컨테이너를 나누고 운영 DB에 직접 접근하지 않도록 구성한 상태예요. 문제 사이의 연결도 더 잘게 나누는 건 다음에 손볼 부분이에요. [Compose 설정 보기](https://github.com/chihun1111/CTF_KDU/blob/c042607b76563c51f99758901d120d92f2f6b8af/infra/docker/docker-compose.yml)

## 같은 문제를 풀어도 플래그는 각자

플래그는 문제를 풀고 정답으로 제출하는 문자열이에요. 이 사이트에서는 참가자마다 다른 플래그를 쓰도록 했어요. 같은 문제를 풀어도 정답이 각자의 계정에 연결되는 방식이에요.

그러려면 문제 서비스가 백엔드에 자료를 요청할 때 두 가지를 확인해야 해요. 어느 문제 서비스에서 온 요청인지, 그리고 누구의 자료를 가져오려는지예요.

먼저 문제 번호에 맞는 서비스 토큰인지 검사하고, 참가자의 로그인 세션도 확인해요. 그 세션에서 찾은 사용자 ID와 문제 번호로 플래그를 가져와요. 예를 들어 03번 서비스의 토큰만 가지고는 자료를 받을 수 없고, 유효한 참가자 세션도 함께 있어야 해요.

사용자 ID를 요청에 적어 보내는 것만으로 다른 사람의 자료를 고를 수 없게 하는 게 여기서 중요한 부분이에요. 서비스 확인과 사용자 확인을 따로 해두니, 각각 무엇을 검사하는지도 더 분명해졌어요. [플래그 조회 코드](https://github.com/chihun1111/CTF_KDU/blob/c042607b76563c51f99758901d120d92f2f6b8af/apps/backend/src/internal/internal-flag.service.ts)

## 이번에 맞힌 개수와 완료 여부는 따로

플래그를 전부 찾기 전에도 일부를 제출해서 확인할 수 있게 했어요. 그러다 보니 화면에 보여 주는 정답 개수의 기준을 정해야 했어요. 현재는 **가장 최근에 제출한 내용**을 기준으로 표시해요. 최종 완료는 8개를 한 번에 제출했을 때예요.

예를 들면 이렇게 돼요.

| 제출한 내용 | 표시되는 정답 수 | 완료 여부 |
| --- | ---: | --- |
| 1~3번 정답만 제출 | 3개 | 아직 |
| 다음에 4~8번 정답만 제출 | 5개 | 아직 |
| 8개 정답을 함께 제출 | 8개 | 완료 |
| 완료 후 정답 2개만 다시 제출 | 2개 | 완료 유지 |

여러 번 나눠 맞힌 것이 자동으로 합쳐지지는 않아요. 대신 한 번 완료했다면 이후에 일부만 다시 제출해도 완료한 기록은 남아요. 그래서 제출 기록과 완료 기록을 따로 두고, 관리자 화면에서도 각각 볼 수 있게 했어요.

저장할 때는 제출 요약과 문제별 결과, 감사 기록을 하나의 트랜잭션으로 묶었어요. 전부 맞았을 때는 완료 기록과 인증 화면용 토큰도 함께 만들어요. 중간에 저장이 실패해서 제출 기록만 있고 결과가 없는 상태를 피하려는 구성이에요. 같은 정답을 여러 칸에 넣었을 때 중복으로 점수가 올라가지 않는지도 처리했어요. [제출 처리 코드](https://github.com/chihun1111/CTF_KDU/blob/c042607b76563c51f99758901d120d92f2f6b8af/apps/backend/src/submissions/final-submit.service.ts)

완료 인증 토큰은 5분 동안 유효하고 한 번만 쓸 수 있어요. 같은 화면을 두 탭에서 동시에 연다고 가정하면, 두 요청이 모두 사용 전 상태를 읽을 수 있겠죠. 그래서 DB를 갱신할 때도 아직 사용하지 않은 토큰인지 다시 확인하고, 실제로 갱신한 요청만 통과하게 했어요. 나중에 8개 정답을 다시 제출하면 새 토큰은 받을 수 있어요. [인증 토큰 처리 코드](https://github.com/chihun1111/CTF_KDU/blob/c042607b76563c51f99758901d120d92f2f6b8af/apps/backend/src/submissions/clear-certificate-drizzle.store.ts)

## 접속자 숫자와 로그인은 나눴어요

로그인 상태는 PostgreSQL에 저장한 세션으로 확인해요. 만료됐거나 로그아웃한 세션인지 보고, 유효하면 해당 사용자의 정보와 역할을 가져와요.

Redis는 관리자 화면의 최근 접속 현황을 계산하는 데 써요. Redis를 사용할 수 없거나 집계할 값을 얻지 못하면, DB에 남은 최근 세션 활동으로 숫자를 구해요. 접속 현황을 보여 주는 기능과 로그인을 판단하는 기능의 기준을 나눠 둔 거예요.

다만 이 숫자는 정확한 사람 수와는 달라요. 최근에 활동한 세션을 세는 방식이고, Redis를 쓸 때와 DB로 대신 계산할 때의 시간 범위도 조금 달라요. 그래서 응답에 집계 출처와 시간 범위를 함께 넣었어요. 관리자 화면에 숫자를 붙일 때도 무엇을 센 값인지 정해 두는 게 필요했어요. [접속 현황 집계 코드](https://github.com/chihun1111/CTF_KDU/blob/c042607b76563c51f99758901d120d92f2f6b8af/apps/backend/src/presence/online-count.service.ts)

## 서버에 올린 뒤에도 남은 것들

배포 쪽은 다시 실행하는 방법과 데이터를 복구하는 방법까지 운영 문서에 정리했어요. 특히 DB 백업만 있으면 끝이라고 생각하기 쉬운데, 암호화한 데이터를 읽으려면 키도 함께 보관해야 해요. 키를 바꿀 때도 기존 데이터를 어떻게 옮길지 먼저 정해야 하고요.

외부 접속에는 HTTPS 설정도 필요해요. 기본 Nginx는 HTTP로 받지만 세션 쿠키에는 `Secure`가 붙어 있어요. 앞에 TLS 프록시를 추가한다면 실제 사용자 IP를 어떻게 전달할지도 같이 확인해야 해요.

사용자 흐름을 검사하는 스크립트는 테스트 계정을 만들고, 일부는 관리자 권한이나 힌트 공개 상태까지 바꿔요. 그래서 별도 리허설 DB에서 실행하도록 안내를 남겼어요. 복원도 별도 환경에서 해보고 로그인과 제출까지 확인하는 순서로 적어 두었어요. [운영 문서 보기](https://github.com/chihun1111/CTF_KDU/blob/c042607b76563c51f99758901d120d92f2f6b8af/docs/operations.md)

다음에 해볼 것도 남아 있어요. 지금은 백엔드와 문제 서비스를 하나씩 실행하는 구성이에요. 일부 제한과 문제 상태가 메모리에 있어서 여러 개로 늘리려면 상태를 공유하는 방법부터 정해야 해요. 비밀번호 재설정이나 키 이전 도구도 아직 없고요.

다음에는 이런 부분을 하나씩 붙여 보고, 예상 참가자 수에 맞춰 부하도 확인해 보려고 해요. 바꾼 내용이 쌓이면 또 글로 남겨볼게요.
