# CTF 플랫폼을 만들며 배운 인증·제출·운영의 경계

개인별 플래그를 누가 요청할 수 있는지, 제출과 완료는 무엇이 다른지. CTF 플랫폼의 인증·트랜잭션·접속 현황·복구 설계를 돌아본다.

작성일: 2026-11-26

CTF 대회를 위한 웹 페이지를 만들면서 서버 구축과 배포, 참가자 진행 상황을 확인하는 관리자 기능까지 혼자 맡았다. 참가자는 문제를 열고 플래그를 제출하지만, 그 짧은 동작 뒤에는 계정과 세션, 개인별 정답, 제출 기록, 완료 인증이 연결되어 있다. 내가 이 프로젝트에서 정리하고 싶은 경험도 이 연결을 하나의 서비스로 만든 과정이다.

현재 플랫폼은 Next.js와 NestJS를 중심으로 PostgreSQL, Redis, Nginx, 8개의 문제 서비스를 묶은 구조다. 화면과 API, 공통 설정, Drizzle 스키마를 TypeScript 모노레포에서 관리하고 Docker Compose로 실행한다. 11월에 인증과 제출, 운영 흐름을 보강하면서 각 구성 요소가 어떤 상태를 책임져야 하는지 더 분명하게 나눴다.

## 문제 서비스에서 운영 데이터까지 닿는 경로

CTF 문제에는 의도적으로 취약한 동작이 들어간다. 참가자가 문제를 분석하는 동안에도 계정 정보와 다른 참가자의 데이터, 대회 운영 기능은 별도로 지켜져야 한다. 그래서 문제를 실행하는 컨테이너와 운영 데이터를 저장하는 영역을 구분했다.

외부 요청은 Nginx로 받고, 화면·API·문제 경로에 따라 각 서비스로 전달한다. PostgreSQL과 Redis는 내부 데이터 네트워크에 둔다. 문제 컨테이너에는 데이터베이스 비밀번호나 전체 플래그 암호화 키를 주지 않고, 자기 문제 번호에 해당하는 내부 서비스 토큰만 전달한다. 필요한 데이터는 백엔드의 제한된 API를 거쳐 받는 구조다. 이 방식에서는 문제 하나의 코드를 수정할 때도 운영 데이터에 대한 직접 접근 권한까지 함께 다룰 필요가 없다. [Compose의 서비스·네트워크 구성](https://github.com/chihun1111/CTF_KDU/blob/c042607b76563c51f99758901d120d92f2f6b8af/infra/docker/docker-compose.yml)

진입점에서도 요청 정보를 정리했다. Nginx는 외부의 `/internal/` 접근을 막고, 클라이언트가 보낸 사용자 식별 헤더와 내부 서비스 헤더를 제거한다. 사용자 신원은 이후의 세션 검증에서 결정한다. `X-Forwarded-For` 역시 클라이언트가 적어 보낸 값을 유지하지 않고 Nginx에 직접 연결한 주소로 설정한다. 프록시 설정 하나가 인증과 속도 제한의 전제에 영향을 준다는 점을 이 구성에서 함께 다뤘다. [Nginx 요청 처리](https://github.com/chihun1111/CTF_KDU/blob/c042607b76563c51f99758901d120d92f2f6b8af/infra/nginx/nginx.conf)

## 개인별 정답을 받을 때 확인하는 두 가지 권한

플래그는 참가자마다 다르게 발급한다. 같은 문제를 풀더라도 제출하는 값은 각자의 계정에 연결된다. 서버에는 정답 비교용 해시와 문제 서비스에 원문을 전달할 때 쓰는 암호문을 나누어 보관한다. 비교하는 일과 원문을 제공하는 일이 서로 다른 경로이기 때문이다. [개인별 플래그 발급](https://github.com/chihun1111/CTF_KDU/blob/c042607b76563c51f99758901d120d92f2f6b8af/apps/backend/src/flags/flag-issuance.service.ts)

이렇게 개인별 자료를 만들면 내부 API에도 두 종류의 확인이 필요하다. **요청한 문제 서비스가 맞는지**, 그리고 **어느 참가자의 자료를 요청하는지**다.

현재 내부 플래그 API는 먼저 문제 번호에 맞는 서비스 토큰을 검사한다. 이어 요청에 포함된 참가자 세션을 검증하고, 세션에서 얻은 사용자 ID와 문제 번호로 플래그를 조회한다. 문제 서비스가 임의의 사용자 ID를 지정하는 방식으로 권한을 넘기지 않았다.

예를 들어 03번 서비스의 토큰이 유효하더라도 그것만으로 참가자 자료를 받을 수는 없다. 유효한 참가자 세션이 함께 필요하다. 반대로 참가자가 로그인한 상태여도 문제 서비스의 토큰까지 대신할 수는 없다. 이 둘을 함께 확인해야 “이 서비스가 이 참가자의 이 문제를 처리한다”는 요청의 범위가 정해진다. [내부 플래그 API의 권한 검사](https://github.com/chihun1111/CTF_KDU/blob/c042607b76563c51f99758901d120d92f2f6b8af/apps/backend/src/internal/internal-flag.service.ts)

## 이번 제출의 결과와 완료 이력을 구분하기

참가자는 8개 플래그를 모두 찾기 전에도 일부를 제출해 확인할 수 있다. 이 기능을 넣으면서 화면에 표시하는 점수의 의미도 정해야 했다. 현재 정답 수는 **가장 최근 제출한 묶음의 결과**다. 여러 번에 나눠 제출한 정답이 자동으로 합쳐져 완료되는 방식은 아니며, 최종 완료에는 8개를 한 번에 제출해야 한다.

예를 들어 다음과 같은 제출 순서를 생각할 수 있다.

| 제출 내용 | 최근 제출의 정답 수 | 완료 이력 |
| --- | ---: | --- |
| 1~3번 정답만 제출 | 3개 | 없음 |
| 다음에 4~8번 정답만 제출 | 5개 | 없음 |
| 8개 정답을 한 번에 제출 | 8개 | 생성됨 |
| 완료 후 정답 2개만 다시 제출 | 2개 | 유지됨 |

마지막 행이 중요하다. 최근 제출 결과는 바뀌어도 이미 완료한 사실까지 지워지면 안 된다. 그래서 제출 기록과 완료 기록을 별도로 두었다. 운영 화면도 최신 정답 수, 제출 횟수, 완료 여부를 각각 보여 준다. 이 구분이 있어야 운영자가 “이번 입력이 맞았는가”와 “이 참가자가 완료한 적이 있는가”를 따로 판단할 수 있다. [최근 제출과 완료 이력 조회](https://github.com/chihun1111/CTF_KDU/blob/c042607b76563c51f99758901d120d92f2f6b8af/apps/backend/src/admin/admin-operations-drizzle.store.ts)

제출 처리에서는 먼저 입력 형식과 허용 항목을 검사하고, 해당 참가자의 정답 해시들과 비교한다. 같은 정답을 여러 칸에 넣어 중복으로 점수를 얻지 않도록 이미 일치한 항목도 추적한다. 이후 제출 요약, 문제별 결과, 감사 기록을 하나의 트랜잭션 안에 저장한다. 전부 맞았다면 완료 기록과 인증 화면용 토큰도 같은 작업에 포함한다.

내가 이 흐름에서 묶은 것은 함께 남아야 하는 데이터다. 제출 기록만 저장되고 문제별 결과가 빠지거나, 완료를 반환했는데 인증에 필요한 토큰이 없다면 다음 화면에서 서로 다른 상태를 보게 된다. 트랜잭션은 이 변경들을 함께 확정하거나 함께 되돌리는 경계다. 감사 기록에는 제출 수와 정답 수, 완료 여부를 남기며 플래그 원문은 넣지 않는다. [최종 제출과 트랜잭션 범위](https://github.com/chihun1111/CTF_KDU/blob/c042607b76563c51f99758901d120d92f2f6b8af/apps/backend/src/submissions/final-submit.service.ts)

완료 인증에는 또 하나의 경계가 있다. 인증 화면용 토큰은 5분 동안 유효하고, 같은 토큰은 한 번만 소비한다. 같은 인증 화면을 두 탭에서 거의 동시에 열었다고 가정하면, 두 요청이 모두 “아직 사용하지 않은 토큰”을 조회할 수 있다. 조회 후 사용 처리만 하면 두 요청이 모두 통과할 여지가 생긴다.

그래서 실제 갱신 조건에도 사용자와 토큰 해시, 만료 여부, `consumedAt`이 비어 있다는 조건을 다시 넣었다. 갱신된 행이 정확히 하나일 때만 인증 정보를 반환한다. 동시 요청의 최종 판단을 데이터베이스의 조건부 갱신에 맡긴 것이다. 한 번만 쓸 수 있는 대상은 이 토큰이며, 이후 8개 정답을 다시 제출하면 새 토큰은 발급될 수 있다. [인증 토큰의 조건부 소비](https://github.com/chihun1111/CTF_KDU/blob/c042607b76563c51f99758901d120d92f2f6b8af/apps/backend/src/submissions/clear-certificate-drizzle.store.ts)

## 로그인 판정과 접속 현황 집계의 역할 나누기

운영자 화면에는 접속 현황이 필요하지만, 이 숫자를 계산하는 기능과 로그인을 허용하는 기능은 다른 책임을 갖는다. 현재 세션 인증의 기준은 PostgreSQL이다. 브라우저가 보낸 세션 토큰을 해시로 변환해 조회하고, 만료 시각과 폐기 여부를 확인한 뒤 사용자의 역할을 읽는다. 로그아웃한 세션이나 만료된 세션을 거르는 판단도 이 데이터에 둔다. [활성 세션 조회](https://github.com/chihun1111/CTF_KDU/blob/c042607b76563c51f99758901d120d92f2f6b8af/apps/backend/src/auth/session-auth-drizzle.store.ts)

Redis는 최근 접속 현황을 계산하는 캐시로 사용한다. 캐시를 사용할 수 없거나 유효한 수를 얻지 못하면 데이터베이스의 최근 세션 활동으로 계산을 이어 간다. 캐시의 장애가 로그인 판정의 기준까지 바꾸지 않도록 역할을 나눈 셈이다.

여기서 숫자의 이름도 중요하다. Redis 집계는 최근 90초, DB 대체 집계는 최근 120초의 세션 활동을 기준으로 한다. 그래서 결과에는 집계 출처와 시간 범위를 함께 담는다. 화면의 값은 최근 활동이 있는 **세션 수**이며, 고유 참가자 수나 현재 연결된 사람 수와 정확히 같지는 않다. 수치만 보여 주는 것보다 무엇을 센 값인지 설명할 수 있어야 운영에 도움이 된다. [접속 현황 집계와 DB 대체 경로](https://github.com/chihun1111/CTF_KDU/blob/c042607b76563c51f99758901d120d92f2f6b8af/apps/backend/src/presence/online-count.service.ts)

## 배포 설정과 복구 절차를 함께 남기기

서버 구축과 배포를 직접 맡으면서 코드와 운영 설정을 하나의 흐름으로 정리했다. 현재 운영 가이드에는 설치와 데이터베이스 초기화, 배포 전 점검뿐 아니라 백업·복원, 비밀값 교체, 사용자 흐름 리허설까지 포함되어 있다.

먼저 외부 접속 조건을 맞춰야 한다. 세션 쿠키는 `Secure`이고 기본 Nginx 진입점은 HTTP이므로 실제 외부 서비스에는 TLS 구성이 필요하다. 앞에 TLS 프록시를 더 두면 Nginx가 보는 직접 연결 주소도 달라진다. 이때 모든 참가자를 프록시 한 대의 IP로 집계하지 않도록 신뢰 프록시 설정과 속도 제한 기준을 함께 검토해야 한다.

복구에서는 데이터와 키를 함께 생각한다. 데이터베이스 백업이 있어도 암호화 키를 잃으면 암호문을 읽을 수 없다. 조회용 비밀값을 바꾸면 기존 해시와 새로 계산한 값도 달라진다. 그래서 키 교체를 설정 파일의 값을 바꾸는 작업만으로 취급할 수 없다. 이전 데이터의 복호화와 재암호화, 해시 재계산이 필요한지부터 구분해야 한다.

검사 자체가 만드는 데이터도 고려했다. 사용자 흐름을 확인하는 smoke 스크립트는 테스트 계정을 만들고, 일부는 운영자 권한과 공개 힌트 상태를 변경한다. 운영 문서에서는 이 검사를 별도 리허설 데이터베이스에서 수행하도록 분리한다. 복원도 같은 방식으로 별도 환경에서 로그인과 제출 흐름까지 확인해야 복구 절차가 구체적이 된다. [운영·백업·복원 가이드](https://github.com/chihun1111/CTF_KDU/blob/c042607b76563c51f99758901d120d92f2f6b8af/docs/operations.md)

## 지금 남아 있는 경계

현재 문제 서비스 8개는 개별 컨테이너로 실행되지만 하나의 문제 네트워크를 공유한다. 문제 간 네트워크 격리를 더 세밀하게 만들 여지가 있다. 백엔드와 문제 서비스도 단일 인스턴스 구성을 전제로 하며, 인증 속도 제한과 일부 문제 상태가 프로세스 메모리에 있어 복제본을 늘리기 전에는 공유 상태와 요청 배치를 설계해야 한다.

비밀값 파일 권한과의 호환성 때문에 일부 서비스가 root로 실행되는 점, 비밀번호 재설정과 암호화 키 이전 도구가 없는 점도 다음 보강 대상으로 남아 있다. 예상 참가자 수에 맞춘 부하 리허설 역시 실제 배포 환경에서 확인할 항목이다.

이 프로젝트를 통해 화면의 버튼 하나가 어떤 데이터를 바꾸고, 그 변경을 누가 허용하며, 중간에 실패하면 무엇을 남겨야 하는지까지 연결해 볼 수 있었다. 앞으로 개발과 서버 운영을 기록할 때도 이 연결을 중심에 두려 한다. 내가 만든 기능의 동작과 함께, 그 기능을 유지하고 복구하는 방법까지 설명할 수 있는 글을 쌓아 가고 싶다.

기록 기준: 2026년 11월 16일의 `c042607` 커밋. 기술 설명은 해당 코드와 운영 문서에 근거하며, 초기 배포 이후의 보강 내용을 포함한다. 운영 규모에 대한 부하 측정은 이 글의 검증 범위에 포함하지 않았다.
