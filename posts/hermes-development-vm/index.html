온라인인 Discord 봇이 답하지 않던 이유

봇은 온라인인데 왜 채팅에 답이 없을까요? 메시지를 받는 부분부터 결과 전송, CLI 호출까지 하나씩 고친 이야기예요.

목차

  • 완료 메시지는 있는데 정작 답이 없었어요
  • 자연어 요청을 넘기자 CLI 인자에서 막혔어요
  • 파일을 만들어 달라는 요청이 상태 조회로 바뀌었어요
  • 자체 bridge를 정리하고 공식 Hermes를 설치했어요
  • 지금 남아 있는 것은 다시 접속할 수 있는 VM이에요

2026년 5월, Proxmox에 개발용 VM을 만들고 Discord에서 요청을 받아 Codex로 작업하는 환경을 붙여 봤어요. 처음에는 봇 여섯 개가 모두 온라인으로 표시됐지만 일반 채팅에는 답하지 않았어요. 메시지 수신, 결과 전송, CLI 호출, 요청 분류를 차례로 고치면서 간단한 계산과 파일 생성까지 시험했어요.

이때 처음 사용한 것은 OMX와 Codex를 연결한 자체 Discord bridge였어요. 이를 시험한 다음 날인 5월 27일, 기존 구성을 정리한 뒤 공식 Hermes Agent를 설치했어요. 같은 VM에서 진행했고 이름도 Hermes로 묶여 있었지만, 두 실행 환경의 설치 과정과 동작 결과는 달라요.

먼저 VM과 도구를 준비했어요

5월 26일 처음 만든 VM은 Ubuntu 24.04.4 LTS에 4 vCPU, 메모리 16GB, 부팅 디스크 80G 구성이에요. 네트워크는 Proxmox의 vmbr0에 연결하고 DHCP를 사용했어요. 작업용 Mac의 공개키를 VM 사용자 계정에 등록해 SSH로 들어갈 수 있게 했어요.

처음 준비한 항목당시 구성
Node.js / npm22.22.2 / 10.9.7
Codex CLI0.133.0
oh-my-codex0.18.3
Tailscale1.98.3, 설치 후 미인증·비활성
컨테이너 도구rootless Podman, overlay 동작 확인
자체 에이전트 사용자 서비스disabled / inactive
systemd lingerno

도구 설치와 실제 작업 시작을 한꺼번에 처리하지는 않았어요. 최초 구성에서는 Codex 로그인과 Tailscale 인증을 수동으로 마무리할 항목으로 남겼어요. 에이전트 실행용 사용자 서비스와 runner는 만들었지만 실행 표식이 없었고, tmux 세션도 없었어요. 재부팅 뒤에도 이 비활성 상태가 유지되는 것까지 확인했어요. 이때의 재부팅 검증은 에이전트 자동 실행 성공을 뜻하지는 않아요.

봇 여섯 개가 온라인이어도 채팅에는 답하지 않았어요

같은 날 오후 자체 bridge를 VM의 tmux 세션에서 실행했어요. Discord Gateway에서 봇 여섯 개가 모두 READY가 됐고, 로그 채널로 보낸 시험 메시지는 HTTP 200을 받았어요. /hermes-status 명령 등록도 성공했어요. bridge를 다시 시작한 뒤에도 같은 결과가 나왔어요.

그런데 일반 채팅을 보내면 답이 없었어요. bridge 프로세스는 살아 있었고 heartbeat 응답도 들어왔어요. 코드를 보니 슬래시 명령을 받는 INTERACTION_CREATE 처리는 있었지만, 채팅 메시지를 받는 MESSAGE_CREATE 처리가 빠져 있었어요. 봇은 온라인이었지만 일반 채팅을 받는 처리가 없었어요.

요청을 받아 작업으로 넘기는 처리를 추가하고 /hermes-task와 봇 멘션 경로를 붙였어요. 일반 채팅을 받는 봇에는 Message Content를 포함한 intent를 적용했어요. 이후에는 MESSAGE_CREATE 진단과 REST polling 보완 경로도 넣었어요. Gateway에서 놓친 메시지를 채널 조회로 읽을 수 있게 한 거예요.

이 단계에서는 polling 요청이 HTTP 200을 받았고, 최근 사람이 보낸 메시지에 본문이 들어 있는 것도 확인했어요. 합성 메시지를 넣은 자체 시험에서는 작업이 완료되고 역할별 진행 메시지가 Discord에 올라왔어요. 다만 이것만으로 실제 대화 흐름이 완성된 것은 아니었어요. 다음 문제는 결과를 어디로 보내느냐였어요.

완료 메시지는 있는데 정작 답이 없었어요

Discord에는 접수·진행·완료 안내가 뜨는데 요청한 채널에 답변 본문이 나타나지 않았어요. 최종 결과는 로그 채널에만 보내고, 원래 채널에는 결과를 로그에 올렸다는 안내만 보내고 있었어요.

최종 결과를 요청이 시작된 채널에 직접 보내고, 로그 채널에는 같은 내용을 복사하도록 바꿨어요. 함께 발견한 문제도 있었어요. 본문이 비어 있는 Gateway 이벤트를 먼저 받으면, 해당 메시지를 이미 처리한 것으로 표시했어요. 나중에 REST polling으로 본문을 읽어도 중복 메시지로 판단해 건너뛸 수 있었어요.

본문이 없거나 실행 조건에 해당하지 않는 이벤트는 처리 완료로 표시하지 않도록 고쳤어요. 다시 실행한 뒤 요청 채널에서 완료 표시와 서버·에이전트 상태 본문이 함께 있는 최종 메시지를 확인했어요. 이제 “끝났다”는 알림과 함께 실제 결과도 읽을 수 있게 됐어요.

자연어 요청을 넘기자 CLI 인자에서 막혔어요

채널 응답을 고친 뒤에는 자연어 요청에서 Codex CLI 오류가 그대로 돌아왔어요.

Text
unexpected argument '--ask-for-approval'

VM에 설치된 Codex CLI는 0.133.0이었어요. bridge가 넘기는 예전 승인 정책 인자를 이 버전의 codex exec가 받지 못했어요. 당시 버전에 맞는 설정 인자로 호출을 고친 뒤, 직접 실행 시험에서는 OK가 나왔어요. bridge를 통과하는 자연어 시험에서는 2+2에 4가 반환됐고 종료 코드도 0이었어요.

실패를 완료로 표시하던 부분도 같이 고쳤어요. Codex가 0이 아닌 코드로 끝나면 codex_error로 남기고 오류를 요약하도록 했어요. 작업 완료 알림만 보고 성공으로 판단하지 않으려면, 프로세스의 종료 결과와 실제 답변이 함께 있어야 했어요.

파일을 만들어 달라는 요청이 상태 조회로 바뀌었어요

이번에는 agent-todo.md 파일을 만들어 달라는 요청에 서버 상태만 돌아왔어요. 상태 조회 분류기가 agent, 에이전트, server, 서버처럼 넓은 단어를 잡고 있었어요. 에이전트 작업 목록을 작성하는 요청도 그 단어가 들어갔다는 이유로 상태 조회에 빠졌어요.

만들, 작성, 파일, .md처럼 실제 작업을 나타내는 표현이 있으면 Codex 실행으로 보내도록 분류를 고쳤어요. 반대로 서버 성능이나 에이전트 상태를 묻는 표현은 기존 상태 조회로 보냈어요. 같은 두 요청을 넣어 각각 CODEX와 STATUS로 나뉘는 것을 확인했어요.

분류를 고쳐도 파일 생성은 한 번 더 막혔어요. 당시 VM에서는 workspace-write 환경의 apply_patch와 bubblewrap 관련 오류로 쓰기가 실패했어요. 시험 중에는 실행 격리를 완화한 조건에서 파일 생성이 되는 것을 확인했고, 작업 공간 밖으로 나가지 않도록 하는 bridge 검사와 프롬프트 제한은 남겼어요. 이 조건은 격리를 유지한 운영 구성이 아니어서 그대로 운영 절차로 삼을 수는 없었어요.

그 시험에서는 작업 공간에 agent-todo.md가 생성됐고, 번호가 붙은 항목 10개와 종료 코드 0을 확인했어요. 한편 관리자 채널의 권한 설정은 HTTP 403으로 실패한 부분이 남아 있었어요. 파일 생성 성공과 별개로, 인증·권한 구성이 모두 끝난 상태는 아니었어요.

자체 bridge를 정리하고 공식 Hermes를 설치했어요

5월 27일 새벽에는 에이전트 관련 프로그램과 작업물을 정리하고 개발용 VM을 다시 준비했어요. VM과 Tailscale·SSH 접속 경로는 유지했어요. 이어 설치한 공식 Hermes Agent는 0.14.0이며, Python 3.11.15와 Codex CLI 0.133.0, Node.js 22.22.3 구성이었어요.

이때 공식 Hermes의 hermes-gateway.service는 사용자 서비스로 등록됐고 enabled, active 상태였어요. 다만 로그에는 활성화된 메시징 플랫폼이 없다는 경고가 있었어요. 모델과 플랫폼 인증·허용 사용자 설정도 마무리할 항목으로 남았어요. Discord 메시지와 파일 생성 시험은 앞서 사용한 자체 bridge에서 수행한 것이고, 공식 gateway는 실행 상태를 확인하는 데까지 진행했어요.

linger도 시점을 구분해서 봐야 해요. 당시 최종 교정 뒤의 값은 Linger=no였어요. gateway가 실행 중이어도 로그아웃 뒤의 지속 실행까지 확인한 것은 아니에요. systemd의 loginctl 문서에서 설명하는 linger는 사용자 서비스 관리자의 생명주기에 관한 설정이며, 서비스 설치나 플랫폼 설정을 대신하지는 않아요.

지금 남아 있는 것은 다시 접속할 수 있는 VM이에요

2026년 10월 22일에는 개발용 VM이 실행 중이고 할당 메모리는 8GiB였어요. 5월에 처음 만든 16GB 구성과는 달라져 있었어요. Tailscale 주소를 통한 직접 SSH 접속은 됐고 tailscaled와 ssh는 모두 active였어요.

반면 hermes 명령은 현재 사용자 PATH에서 찾지 못했고, hermes-gateway.service는 LoadState=not-found, ActiveState=inactive였어요. 이때 linger는 yes였어요. 5월의 실행 결과가 현재까지 이어지는 것도 아니고, linger가 켜져 있다고 현재 등록돼 있지 않은 gateway가 생기는 것도 아니에요. 다시 작업을 시작할 때는 이 접속 가능한 VM 위에서 실행 파일과 서비스, 모델·메시징 설정부터 맞춰야 해요.

접속 경로는 Tailscale과 SSH로 홈서버에 접속하기에 정리했어요.
