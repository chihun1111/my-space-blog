Proxmox에 올린 TrueNAS, 실제 디스크와 공유 구성

Proxmox에 TrueNAS를 올리고 디스크와 SMB 공유를 연결했어요. 저장소 구성과 백업에서 따로 챙길 부분을 정리했어요.

Chihun2026년 10월 18일수정 2026년 11월 26일11분 읽기

홈랩에서 Proxmox에 TrueNAS를 VM으로 올려 쓰고 있어요. 한 서버 안에서 가상머신과 NAS가 함께 돌아가다 보니, 어떤 공간에 무엇을 두느냐에 따라 부팅과 백업의 의존 관계도 달라져요.

사용 중인 버전은 Proxmox VE 9.2.11과 TrueNAS 25.10.5예요. 아래는 2026년 10월 18일 기준의 구성이에요.

TrueNAS가 먼저 켜질 수 있게

TrueNAS의 부팅·EFI 디스크는 호스트 NVMe의 local-lvm에 있어요. LVM-thin 볼륨으로 부팅 공간을 로컬에 두면, NAS를 켜기 위해 NAS 공유부터 열어야 하는 상황을 피할 수 있어요.

항목설정
CPU1소켓 · 6코어, cpu: host
메모리24576 MiB = 24 GiB
머신 · 펌웨어q35 · OVMF(UEFI)
부팅 디스크local-lvm, 64 GiB
EFI 디스크같은 local-lvm, 4 MiB
디스크 컨트롤러virtio-scsi-single
게스트 에이전트agent: 1, 활성화

자동 시작은 onboot: 1, 시작 순서와 간격은 order=10,up=10이에요. 이 VM을 시작하고 다음 VM까지 10초를 기다리지만, SMB가 준비됐는지 확인하는 과정은 아니에요. 재부팅 후 공유가 열리는 시점은 별도로 확인해야 해요. 시작 순서와 간격

VirtIO NIC는 호스트의 물리 인터페이스와 연결된 vmbr0를 사용해요. firewall=1도 켜져 있지만 실제 허용 범위는 방화벽 규칙에 달려 있어요.

부팅 볼륨을 호스트 쪽에서 따라가면 64G LVM 볼륨, LVM-thin 풀, NVMe 파티션, 물리 NVMe 순서로 이어져요. TrueNAS의 EFI 디스크도 이 로컬 저장소에 있어요. 아래의 데이터용 HDD 세 개와 운영체제를 담는 저장 공간이 서로 분리돼 있는 셈이에요.

Text
TrueNAS 부팅
호스트 NVMe → local-lvm → 64G 시스템 디스크 + EFI 디스크

NAS 파일
물리 HDD → QEMU SCSI 장치 → TrueNAS의 ZFS 풀 → 데이터셋 → SMB 공유

이 두 경로를 따로 보면 장애가 난 위치에 따라 확인할 곳도 달라져요. VM 자체가 부팅하지 않는다면 로컬 부팅 볼륨과 VM 설정이 먼저이고, 부팅 뒤 특정 공유만 열리지 않는다면 ZFS 풀·데이터셋·SMB 쪽으로 범위가 좁아져요. 실제 장애를 재현한 결과가 아니라 이 구성의 연결 관계를 설명한 거예요.

운영체제 밖에 두는 데이터

파일을 담는 공간은 호스트의 물리 디스크를 by-id로 연결해요. 아래 설정의 꺾쇠 부분만 장비 식별자를 바꾼 거예요.

Text
scsi0: local-lvm:<부팅 볼륨>,discard=on,iothread=1,size=64G,ssd=1
scsi1: /dev/disk/by-id/<4TB 디스크 A>,backup=0,size=3907018584K
scsi2: /dev/disk/by-id/<4TB 디스크 B>,backup=0,size=3907018584K
scsi3: /dev/disk/by-id/<2TB 디스크>,backup=0,size=1953514584K

부팅 디스크 scsi0에만 discard 전달·별도 I/O 스레드·SSD 표시 옵션이 명시돼 있어요. 데이터 디스크의 backup=0은 뒤의 백업 구성과 이어져요.

TrueNAS는 이 물리 디스크에 QEMU의 가상 SCSI로 접근해서 모델명이 QEMU HARDDISK로 보여요. hostpci 항목은 없는 구성으로, HBA 전체를 넘기는 PCI 패스스루와는 달라요. 디스크 연결 방식

그 위에서 파일을 관리하는 풀은 다음 두 개예요.

풀연결한 디스크상태
tank4TB × 2, 미러 vdev 1개ONLINE
nc_pool2TB × 1, 단일 디스크 vdevONLINE

tank는 용량을 합치는 대신 같은 데이터를 양쪽에 둬서 한 장의 고장에 대비해요. 삭제도 함께 반영되므로 파일을 되찾을 백업은 따로 필요해요. nc_pool에는 중복성이 없어요. 4TB·2TB가 약 3.6TiB·1.8TiB로 보이는 것은 단위 차이예요. 실제 남은 공간은 풀의 사용량에 따라 달라져요. 풀 구성

물리 디스크 연결과 별개로 가상화의 제약도 남아요. TrueNAS 공식 안내는 중요 데이터를 다루는 일반 운영에 가상화를 권장하지 않고, 가상 디스크 기반 풀에도 주의를 요구해요.

TrueNAS 안에서는 부팅용 boot-pool도 ONLINE이었어요. 그래서 운영체제의 풀, 미러로 만든 파일 저장 풀, 단일 디스크 풀을 따로 볼 수 있어요. ONLINE은 당시 풀 상태이고, 파일을 지우고 되살리는 복구 시험 결과는 아니에요.

같은 풀에서 나누는 공유와 권한

일반 파일과 Proxmox 백업은 모두 tank에 둬요. 대신 데이터셋과 SMB 공유를 나눠서 같은 풀 안에서도 경로와 권한을 따로 관리해요.

SMB 공유연결한 경로데이터셋 ACL 모드
share/mnt/tank/shareRESTRICTED
pve-backup/mnt/tank/pve-backupPASSTHROUGH

두 데이터셋은 NFSv4 ACL을 사용해요. 압축은 LZ4, 레코드 크기는 128K, 동기 쓰기 정책은 STANDARD이고, 접근 시각 갱신과 읽기 전용은 모두 OFF예요. 두 공유는 활성화돼 있고 SMB 서비스는 실행 중이며 자동 시작도 켜져 있어요.

Share ACL은 둘 다 Everyone / ALLOWED / FULL이에요. 이 값만으로 누구나 쓸 수 있다는 뜻은 아니에요. 파일 접근에는 아래의 데이터셋 ACL도 적용돼요. 두 ACL의 역할

tank/share에는 소유자·소유 그룹·추가 그룹 하나의 FULL_CONTROL과 읽기·탐색 중심의 사용자·그룹 항목이 함께 있고, 모두 상속 플래그가 설정돼 있어요. 반면 tank/pve-backup은 소유자에게 읽기·쓰기·추가·하위 항목 삭제를 허용하고, 소유 그룹과 everyone@는 읽기·탐색 중심이에요. 이쪽의 모든 항목은 NOINHERIT예요.

이 ACL은 데이터셋 루트 기준이에요. 계정별 읽기·쓰기는 소속 그룹과 하위 파일의 ACL까지 따로 확인해야 해요.

공유를 나눌 때 생기는 차이는 이름만이 아니에요. 일반 파일 경로에는 상속되는 권한이 있고, 백업 경로의 루트 ACL 항목에는 상속하지 않는 설정이 들어 있어요. 그래서 한 공유에 접근한 계정이 다른 공유에도 같은 방식으로 쓸 수 있다고 가정할 수 없어요. 제 구성에서는 공유 이름 → 데이터셋 경로 → 파일시스템 ACL을 이어 봐야 실제 접근 대상을 설명할 수 있어요.

백업은 다시 같은 NAS로 돌아와요

Proxmox는 앞의 pve-backup 공유를 CIFS 저장소 nas-backup으로 연결해요. 부팅 디스크는 로컬에 두지만 VM 백업은 다시 TrueNAS의 tank로 들어오는 셈이에요.

예약 작업 항목설정
실행 여부 · 대상활성화, all=1(전체 게스트 대상)
일정매주 일요일 03:00, Asia/Seoul
대상 저장소nas-backup → SMB pve-backup
백업 모드snapshot
작업의 보관 설정keep-last=4(최근 4개 보관)
저장소의 기본 보관 설정keep-all=1

예약 작업에는 최근 4개를 남기는 조건이 별도로 있어요. snapshot 역시 Proxmox의 백업 모드이고, TrueNAS의 정기 ZFS 스냅샷과는 별개예요. 백업 모드와 보관 설정

현재 남아 있는 TrueNAS VM 백업은 세 개예요. 다만 앞의 backup=0 때문에 데이터 디스크 세 개는 VM 백업에서 빠져요. 부팅 환경을 되살릴 백업과 NAS 파일을 복구할 백업을 나눠 봐야 해요. 디스크별 백업 포함 옵션

VM에서 백업 파일까지의 경로를 펼치면 아래처럼 연결돼요.

Text
Proxmox의 예약 백업 작업
  → CIFS 저장소 nas-backup
  → TrueNAS의 SMB 공유 pve-backup
  → /mnt/tank/pve-backup 데이터셋
  → 4TB 디스크 두 개로 만든 tank 미러

백업 대상이 전체 게스트라고 해도 모든 디스크의 내용이 들어가는 것은 아니에요. 이 NAS VM에서는 디스크별 backup=0이 적용되므로, 남아 있는 VM 백업 세 개를 NAS 파일의 복사본 세 개로 셀 수 없어요. 또 예약 작업의 최근 4개 보관 설정은 현재 파일 개수와 다른 값이에요. 설정은 앞으로 유지할 개수의 조건이고, 세 개는 조회 당시 남아 있던 아카이브 수예요.

백업 파일도 같은 NAS에 있어서 TrueNAS가 멈추면 접근이 어려워져요. 데이터셋을 나눴어도 호스트 밖의 독립된 복사본은 아니에요. 앱 스냅샷은 일부 있지만 TrueNAS에 등록된 정기 스냅샷·복제 작업은 없어요. 외부 파일 백업의 유무와 실제 복구 가능 여부는 아직 확인할 부분이에요.
