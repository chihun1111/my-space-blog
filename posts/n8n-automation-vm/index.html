n8n을 올려 쓴 전용 VM, 자원과 네트워크 설정

Chihun2026년 10월 23일7분 읽기

n8n은 Proxmox에 별도 VM으로 올려 사용했다. NAS 안의 앱으로 넣은 구성이 아니라, CPU와 메모리·시스템 디스크·네트워크 주소를 가진 독립된 환경이다. 홈서버에서 Home Assistant, 데이터 처리, WOL을 각각 나눈 것처럼 n8n도 전용 VM으로 두었다.

지금 남아 있는 구성에서 구체적으로 설명할 수 있는 부분은 이 VM의 자원 배정과 저장소, 고정 주소, 시작 순서다. 워크플로의 노드나 실행 내역까지 복원한 상태는 아니므로, 이 글은 n8n을 올려 쓴 서버 환경에 초점을 맞췄다.

2코어·6GiB와 60G 시스템 디스크

2026년 10월 22일 기준으로 n8n VM에는 CPU 2코어와 메모리 6144MiB를 배정해 뒀다. 메모리를 GiB로 바꾸면 6GiB다. 머신 유형은 q35, 펌웨어는 OVMF이며 CPU 유형은 host다.

항목내 설정
CPU1소켓 · 2코어, host
메모리6144MiB, 즉 6GiB
머신·펌웨어q35 · OVMF
시스템 디스크local-lvm의 scsi0, 60G
SCSI 컨트롤러virtio-scsi-single
네트워크VirtIO NIC → vmbr0

6GiB는 VM에 배정한 메모리다. n8n 프로세스가 실제로 그만큼 사용했다는 측정값도, Node.js 힙 제한을 6GiB로 설정했다는 뜻도 아니다. 같은 호스트의 데이터 처리 VM도 2코어·6GiB를 쓰지만 시스템 디스크는 40G다. 두 VM의 자원이 비슷해도 디스크와 주소는 따로 관리한다.

시스템 디스크는 Proxmox의 로컬 저장소에 있다. NAS 공유를 부팅 디스크로 사용하지 않는다. 디스크 설정에는 discard=on, iothread=1, ssd=1이 함께 들어 있다.

Text
scsihw: virtio-scsi-single
scsi0: local-lvm:<시스템 볼륨>,discard=on,iothread=1,size=60G,ssd=1

볼륨 식별자를 생략한 실제 설정 형태다. discard는 게스트의 discard 요청 전달, iothread는 디스크 I/O 처리 스레드, ssd는 게스트에 알리는 장치 특성과 관련된 옵션이다. 이 옵션만으로 워크플로 처리 속도나 저장소 성능을 평가할 수는 없다. 디스크 연결 방식은 VM 디스크 설정 글에 따로 적었다.

Cloud-Init 매체와 고정 주소를 붙였다

n8n VM에는 시스템 디스크 외에 Cloud-Init용 ide0 매체가 연결돼 있다. 이 매체도 local-lvm에 있으며 CD-ROM 형식이다. Cloud-Init 설정을 게스트에 전달하는 매체와 OS가 들어 있는 60G 시스템 디스크는 역할이 다르다. Proxmox Cloud-Init 문서

네트워크 장치는 VirtIO 방식으로 vmbr0에 연결했다. ipconfig0에는 DHCP 대신 IPv4 주소와 CIDR, 게이트웨이가 명시돼 있다. 주소를 일반화하면 설정의 관계는 아래와 같다.

Text
net0: virtio=<VM MAC>,bridge=vmbr0,firewall=1
ide0: local-lvm:<Cloud-Init 볼륨>,media=cdrom
ipconfig0: ip=<고정 IPv4>/<프리픽스>,gw=<게이트웨이>

개발용 VM의 ipconfig0는 DHCP다. n8n과 데이터 처리 VM은 각각 고정 주소를 지정해 둔 쪽이다. 브리지에 연결하는 설정과 게스트가 사용할 주소를 지정하는 설정이 한 줄에 들어 있지 않으므로 두 항목을 함께 봐야 한다.

firewall=1도 네트워크 장치에 들어 있다. 다만 이 값 하나가 어떤 앱 포트를 허용했는지 설명해 주지는 않는다. VM의 주소, Proxmox 방화벽 규칙, 게스트에서 앱이 수신하는 포트는 서로 다른 설정이다. 고정 주소를 지정해 뒀다는 사실만으로 n8n 웹 화면까지 접속된다고 볼 수는 없다.

NAS와 데이터 VM 뒤에 시작하도록 두었다

호스트 부팅 시 자동 시작하는 옵션을 켜고, 시작 순서를 70으로 지정해 뒀다.

Text
onboot: 1
startup: order=70,up=30
boot: order=scsi0;ide2;net0

startup은 VM 사이의 시작 순서이고 boot는 n8n VM 내부의 부팅 장치 순서다. 이 VM은 시스템 디스크인 scsi0를 먼저 시도한다. 두 곳에 모두 order라는 말이 있지만 정하는 대상은 다르다.

내 홈서버의 자동 시작 순서는 NAS가 10, WOL이 40, Home Assistant와 데이터 처리 VM이 50, n8n이 70이다. n8n의 up=30은 이 VM을 시작한 뒤 다음 대상으로 넘어가기 전의 대기 시간이다. n8n 앱이나 데이터베이스가 준비됐다는 응답을 기다리는 검사는 아니다. VM 자동 시작과 종료 순서

데이터 처리 VM을 먼저 켜도록 뒀더라도 n8n이 그 VM의 PostgreSQL을 사용한다고 단정할 수는 없다. n8n 자체의 저장 방식과 다른 서비스로 연결하는 자격증명·노드는 앱 안에서 별도로 확인해야 하는 설정이다.

VM을 다시 켠 것과 n8n에 접속한 것은 달랐다

10월 22일에는 n8n VM이 중지 상태였다. 23일에 VM을 다시 시작했고 Proxmox의 전원 상태는 running으로 바뀌었다. 자동 시작 옵션이 남아 있는 것과 지금 전원이 켜져 있는 것은 별개의 상태였다.

전원을 켠 뒤에도 내부 확인에는 막히는 부분이 있었다. QEMU 게스트 에이전트는 응답하지 않았고, Tailscale 경로의 SSH 접속은 시간 초과로 끝났다. Proxmox를 거쳐 내부 주소로 접속하면 SSH 서버에는 도달했지만 기존 키 인증이 거절됐다.

n8n의 기본 웹 포트로 시도한 상태 요청에서도 정상 응답을 받지 못했다. 실제 앱이 그 포트에서 수신하는지까지 확인된 상태는 아니므로, 이 결과를 n8n 프로세스가 종료됐다는 증거로 사용하지는 않는다. 현재 확인된 상태는 VM 실행까지다.

이 환경에서 n8n을 올려 쓴 경험은 있지만, 남아 있는 워크플로 이름과 노드 연결, 성공·실패 실행 기록은 아직 열어 보지 못했다. 그래서 특정 서비스 연동이나 자동화 결과를 이 글에 덧붙이지 않았다. VM 설정은 유지돼 있으며 앱 내부 기록은 접속이 복구된 뒤 이어서 남길 부분이다.
