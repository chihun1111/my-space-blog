2026년 11월 19일의 공개 소스와 내 변경 이력을 기준으로 정리한 개발 기록이다.

AI 기능을 웹 서비스에 붙일 때 가장 먼저 눈에 들어오는 것은 모델이 만들어 낸 문장이다. 하지만 실제 사용 흐름을 만들다 보면 그 앞뒤의 일이 훨씬 많아진다. 사용자가 쓴 답변을 언제 저장할지, 모델 응답이 실패하면 어떤 상태로 돌아갈지, 질문을 수정하는 동안 예전 결과가 도착하면 무엇을 버릴지까지 정해야 한다.

내가 참여한 말씨도 이런 문제를 다루는 프로젝트다. 어려움을 겪는 사람 곁의 가족이나 친구가 어떤 말과 행동을 준비할지 정리하도록 돕는 서비스다. 사용자가 목적과 상황을 설명하면 필요한 정보를 확인하고, 대화문과 행동 가이드를 카드로 제공한다. 이 글에서는 그 서비스를 구현하면서 내가 반영한 백엔드·모델 연동·대화 흐름·복구 작업을 기록한다.

말씨는 팀 프로젝트다. 프로젝트 전체를 내 단독 작업으로 소개하기보다, 내 GitHub 계정의 커밋에서 확인할 수 있는 변경을 중심으로 설명한다. 서비스의 목적과 현재 구성은 프로젝트 README에서 볼 수 있다.

화면과 모델 사이에 필요한 상태 만들기

초기 연동 작업에서는 기존 UI에 PostgreSQL 백엔드와 Gemma 상태 에이전트를 연결했다. 이후에는 학습 모델의 JSON 응답과 질문 관리, 서버 기록을 연결하고, 모델 결과가 확인되기 전에 질문이 진행되는 문제와 실패 후 입력을 다시 다루는 흐름을 보완했다.

이 과정에서 중요한 단위는 채팅 말풍선 하나가 아니라 대화의 상태였다. 사용자가 현재 어떤 질문에 답하고 있는지, 답변의 어느 판본을 모델이 읽었는지, 모델 결과를 반영해도 되는지, 마지막 가이드가 저장됐는지를 함께 관리해야 했다.

예를 들어 사용자가 답변을 전송한 직후 모델 요청이 실패했다고 하자. 화면에서 입력을 없애는 것만으로 제출을 완료했다고 처리하면 사용자는 같은 내용을 다시 써야 한다. 반대로 원래 입력과 제출 상태를 보존하면 같은 답변으로 재시도할 수 있다. 요청이 중단된 뒤 화면을 이동하거나 다시 열어도, 지금 작성 중인 내용과 이미 저장한 내용을 구분할 수 있어야 한다.

이런 문제는 로컬 모델과 저장 대화 흐름을 안정화한 변경과 중단된 요청 뒤 초안·화면 이동을 보존한 변경에 반영했다. 모델을 연결하는 작업이 화면, API, 데이터베이스의 상태를 함께 설계하는 일로 이어진 이유다.

질문을 많이 하는 것보다 필요한 것을 묻기

질문은행에 문항이 있다는 이유만으로 모든 문항을 순서대로 묻는 흐름은 사용자의 목적과 어긋날 수 있다. 한 번의 답변에 원하는 도움, 관계, 실제 상황이 이미 들어 있을 수도 있다. 이때 같은 내용을 다시 물으면 답변 부담만 늘어난다.

최근에는 새 대화가 목적과 상황을 먼저 확인하고, 보통 2~4개 질문 안에서 필요한 정보를 얻도록 흐름을 바꿨다. 여기서 2~4개는 사용자 경험을 위한 목표다. 반드시 네 개를 채우는 규칙이 아니며, 모든 실제 모델 실행에서 그 수를 달성했다는 성능 수치도 아니다. 핵심은 답을 알게 되면 결과가 실질적으로 달라지는 정보만 더 묻는 것이다.

현재 분리 모드의 질문 라우터는 세 가지 결정을 반환한다.

결정의미
existing질문은행의 후보 중 필요한 문항 하나 선택
custom기존 문항으로 확인하기 어려운 정보를 짧게 추가 질문
finish현재 답변으로 결과를 준비할 수 있어 질문 종료

질문을 고를 때는 근거가 된 답변의 ID, 원문의 연속된 인용, 그 정보가 필요한 이유도 반환하게 했다. 서버는 모델이 선택한 문항이 실제 후보인지, 인용이 현재 답변에 있는지, 이미 발행한 문항과 등록된 확인 범위가 중복되는지 검사한다. 관련 구현은 질문 라우터와 짧은 질문 흐름에 남겼다.

질문을 줄이는 과정에서 반대 방향의 오류도 생길 수 있다. 사용자가 “상황을 정리하고 싶어요”라고 목적만 알려 줬는데, 정리할 상황까지 충분히 받았다고 판단해 버리는 경우다. 이 경우에는 상황 질문을 먼저 보여 주도록 보완했다. 선택형 입력과 “상황을 정리하고 싶어요.”라는 자유 입력을 검사하고, 이미 구체적 상황을 함께 적은 답변은 다시 묻지 않는 회귀 사례를 추가했다. 해당 수정은 질문 수를 줄이는 것과 필요한 맥락을 놓치지 않는 일을 함께 다뤄야 한다는 사례다.

질문 모델과 최종 카드 모델을 분리하기

다음 질문 하나를 고르는 작업과 전체 답변을 읽어 최종 카드를 만드는 작업은 필요한 문맥과 처리량이 다르다. 그래서 대화 모델과 분석·카드 모델을 나누어 선택하는 구조를 반영했다. 공개 구현에서는 12B와 31B 프로필을 제공하고, 분리 모드에서 질문 라우팅과 최종 생성이 서로 다른 경로를 사용한다.

질문 단계는 최신 답변, 앞선 원문의 필요한 부분, 이미 표시한 질문, 다음 후보를 읽는다. 분리 모드의 모델 호출은 답변 제출당 최대 한 번으로 제한한다. 반면 최종 단계는 암호화해 저장한 대화의 원문을 읽고 기존 카드 생성과 검토를 수행한다. 질문 단계의 짧은 발췌를 최종 결과의 전체 근거처럼 사용하는 구조가 아니다.

최종 카드 작업은 브라우저의 HTTP 요청과 분리했다. 사용자가 답변을 마치면 해당 답변 버전의 작업을 등록하고, 서버의 작업자가 결과를 만든다. 검토를 통과한 카드는 준비되는 순서대로 표시하고, 전체 결과와 기록은 데이터베이스에 저장한다.

브라우저의 연결이 끊어졌다는 이유만으로 생성 결과를 잃지 않도록 하고, 저장 실패를 화면의 성공 표시와 혼동하지 않도록 만드는 것이 이 구조의 목적이다. 모델 크기를 나누었다는 사실만으로 속도나 품질이 보장되지는 않는다. 실제 이점은 동일한 입력과 실행 조건에서 별도로 확인해야 한다.

이 변경은 모델 역할 분리 커밋에 API, 관리자 설정, 마이그레이션, 질문 라우터, 결과 작업자, 회귀 검사와 함께 반영했다.

늦게 도착한 결과를 저장하지 않기

백그라운드 생성에서 까다로운 경우는 사용자가 기다리는 동안 답변을 수정하는 상황이다. 이전 답변을 읽고 시작한 모델이 뒤늦게 성공하더라도, 그 결과를 새 답변의 결과로 저장하면 안 된다.

현재 결과 작업은 대화 ID와 소유자, 답변 버전, 실행 토큰을 기준으로 관리한다. 원문과 모델 출력을 작업 큐에 다시 복사하지 않고, 기존 암호화 대화 저장소를 참조한다. 답변이 바뀌면 이전 버전의 작업을 지우고 새로운 상태에 맞춰 등록한다.

작업자는 데이터베이스에서 실행할 항목을 잠그고 가져온다. 구현에는 FOR UPDATE SKIP LOCKED가 사용되며, 실행 권한에 유효 시간을 두고 주기적으로 갱신한다. 결과를 저장할 때도 작업의 버전과 실행 권한이 유효한지 다시 확인한다. 프로세스가 중단되면 권한이 만료된 작업을 복구할 수 있고, 오래된 작업자가 나중에 돌아와도 현재 결과를 덮어쓰지 못하도록 경계를 둔다.

이런 처리에서 “재시도하면 된다”는 말만으로는 부족하다. 무엇을 재시도하는지, 이전 실행과 새 실행을 어떻게 구분하는지, 중복 저장이나 잘못된 버전의 저장을 어디에서 막는지가 정해져 있어야 한다. 결과 작업자 코드는 그 경계를 다루는 구현이다.

생성된 설명과 사용자의 원문을 구분하기

AI가 만든 질문이나 설명이 어느 순간 사용자가 직접 말한 사실로 바뀌면, 다음 단계의 결과도 잘못된 전제를 따라가게 된다. 따라서 개인화된 질문은 원문 문항 ID와 수정번호, 인용 구간을 함께 갖도록 했다.

서버는 인용을 현재 원문과 다시 대조한다. 사용자가 원문을 고치면 그 원문에서 파생된 추가 질문과 답변도 연쇄적으로 무효화한다. 사용자가 아직 답하지 않은 질문은 답변이 없는 상태로 남긴다. 질문을 건너뛰었다고 해서 그 답을 모델이 만들어 채우지 않는다.

또한 질문 문구와 실제 사용자 답변은 저장 목적이 다르다. 어떤 질문을 보여 주었는지는 대화 이력을 설명하기 위한 데이터이고, 사용자가 보고한 사실의 근거는 실제 답변이다. 이 구분은 개인화 질문의 저장·검증 계약에 정리돼 있다.

대화가 끝난 뒤 새로운 상황을 이어서 다루는 기능에서도 같은 원칙이 필요했다. 후속 대화와 카드 스냅샷 변경에서는 기존 기록을 기준으로 추가 대화를 만들고 새로운 결과를 저장하는 흐름을 API·화면·데이터베이스에 함께 반영했다. 이전 카드와 새 상황의 결과를 구분할 수 있도록 하는 작업이다.

테스트 결과가 무엇을 뜻하는지 기록하기

AI 서비스에서는 테스트가 통과했다는 말에도 범위가 필요하다. 합성 모델 응답으로 저장·복구 경로를 검사한 결과와, 실제 모델이 적절한 질문과 카드를 생성한 결과는 같은 증거가 아니다.

이 프로젝트에서는 질문셋을 JSON으로 작성해 앱의 실제 문답·모델 호출 경로를 재현하는 실행기도 추가했다. 별도의 테스트용 질문 처리기를 만드는 대신 앱의 입력 검증과 상태 전이, 모델 게이트웨이를 재사용한다. 현재 질문에 대응하는 답변이 입력에 없으면 임의로 만들어 진행하지 않고 awaiting_input 상태로 멈춘다.

보고서에는 입력과 소스 식별 정보, 기대값과 실제 결과, 호출 수, 오류와 실행 상태를 남긴다. 여기서도 모델 설정을 조회한 HTTP 요청과 실제 생성 요청을 구분하고, 확인되지 않은 토큰 수를 임의로 채우지 않는다. 질문셋 모델 테스트 실행기와 사용 규격에 그 기준을 남겼다.

11월 18일의 모델 역할 분리 문서에는 로컬 12B의 합성 대화 실행과, 합성 결과 모델을 연결한 PostgreSQL 검사 결과가 각각 기록돼 있다. 후자는 부분 카드 전달, 연결 종료 이후 완료, 답변 수정에 따른 작업 무효화, 장애 재시도, 재시작 복구, 암호화 기록 저장과 재조회를 확인한 범위다. 실제 31B의 최종 생성·검토 시간과 카드 품질은 해당 문서에서 실측 전으로 구분했다. 이 글을 작성하며 그 검사를 다시 실행한 것은 아니며, 공개된 당시의 검증 기록을 기준으로 설명한다.

다음에 더 확인할 것

현재 구현을 바탕으로 다음 단계에서 확인할 것은 분명하다. 실제 모델이 상황을 충분히 이해했을 때 질문을 끝내는지, 필요한 질문을 놓치거나 같은 내용을 되묻지 않는지, 마지막 카드가 검토와 저장까지 완료되는지를 같은 실행 안에서 확인해야 한다.

질문 단계의 응답 시간만으로 전체 사용자 경험을 설명하지 않고, 최종 생성·검토·저장까지 구간을 나눠 볼 필요도 있다. 자동 회귀 검사와 별도로 사람이 질문의 적절성과 원문에 없는 사실의 포함 여부를 검토하는 과정도 남아 있다. 기능 구현과 실모델 검증, 실제 사용 환경의 확인 상태를 계속 구분해 기록하려고 한다.

말씨 작업은 내게 웹 개발과 서버 운영이 만나는 지점을 보여 준다. 화면에 답변이 보이는 순간뿐 아니라, 요청이 실패하고 연결이 끊기고 입력이 바뀌는 순간에도 대화의 의미와 기록이 유지돼야 한다. 앞으로 이 블로그에는 이런 구체적인 문제, 구현한 경계, 확인한 결과와 남은 한계를 함께 기록한다.
