말씨 만들기: 질문은 줄이고, 답변은 안 잃어버리게

질문을 조금만 하고도 필요한 내용을 모을 수 있을까요? 말씨의 질문 흐름과 답변 수정, 결과 저장을 손본 과정을 적어 봤어요.

말씨를 만들면서 질문을 어떻게 이어 가고, 답변을 어떻게 남길지 손본 내용을 정리해 봤어요. 말씨는 HOP Biohealth AI Challenge에서 팀으로 만든 프로젝트예요. 어려움을 겪는 사람 곁의 가족이나 친구가 대화와 행동을 준비하도록 도와줘요. 상황을 입력하면 필요한 내용을 더 묻고, 대화문과 행동 가이드를 카드로 보여 줘요.

저는 화면에 PostgreSQL과 Gemma 모델을 연결하고, 입력 보존과 재시도, 후속 대화, 결과 저장 쪽을 다뤘어요. 이번 글에서는 그중 질문을 줄이고, 답변을 고치거나 연결이 끊겨도 대화가 이어지게 만든 부분을 적어 보려고 해요.

필요한 것만 물어보기

질문 목록이 있다고 전부 물어볼 필요는 없어요. 한 번의 답변에 원하는 도움과 상황이 같이 들어갈 수도 있으니까요. 이미 설명한 내용을 또 물으면 대화만 길어져요.

그래서 새 대화는 목적과 상황부터 확인하고, 보통 2~4개 질문 안에서 필요한 정보를 얻도록 바꿨어요. 네 개를 꼭 채우는 규칙은 아니에요. 그 답을 알아야 결과가 달라지는지를 보고, 필요한 내용이 있을 때만 더 물어보는 방향이에요. 2~4개는 설계 목표라서 실제 모델이 항상 그 수에 맞춰 질문한다는 뜻은 아니고요.

질문을 고르는 모델은 기존 문항 선택, 짧은 추가 질문, 질문 종료 중 하나를 반환해요. 질문을 선택했다면 어떤 답변을 보고 골랐는지 원문 인용도 보내게 했어요. 서버는 그 인용이 실제 답변에 있는지, 이미 나온 문항이나 확인 범위를 반복하는지 검사해요.

줄이는 것만 생각하면 너무 일찍 끝나는 경우도 챙겨야 해요. “상황을 정리하고 싶어요.”라는 답은 원하는 도움만 알려 줘요. 어떤 상황인지는 아직 없으니 여기서는 상황 질문을 먼저 보여 주도록 고쳤어요.

검사에는 해당 선택형 답변과 같은 문장의 자유 입력을 넣었어요. “상황을 정리하고 싶어요. 어제 친구와 말다툼했어요.”처럼 상황을 같이 적은 입력은 같은 방식으로 강제 처리하지 않는지도 확인했고요. 실제 대화 기록이 아니라 이 수정에 넣은 합성 검사 사례예요.

질문과 카드는 나눠서 만들기

다음 질문 하나를 고르는 일과 전체 답변을 읽고 카드를 만드는 일은 필요한 내용이 달라요. 질문 쪽은 최신 답변과 앞선 답변의 필요한 부분, 이미 물은 문항, 다음 후보를 보면 돼요. 최종 카드 쪽은 전체 원문을 읽고 생성과 검토를 거쳐야 하고요.

그래서 질문 모델과 분석·카드 모델을 나눠 선택하는 기능을 반영했어요. 12B와 31B 프로필을 제공하고, 분리 모드의 질문 호출은 답변 제출당 최대 한 번으로 뒀어요. 최종 카드의 생성·검토는 대화가 끝난 뒤 따로 진행해요.

최종 생성은 저장한 전체 답변을 다시 읽어요. 질문할 때 보낸 짧은 발췌만으로 결과를 만들지는 않아요. 대화에 쓰는 모델 연결 버전도 고정해서, 설정을 바꾼 뒤에도 진행 중인 대화는 원래 조건을 유지하도록 했어요.

카드 생성 작업은 브라우저 요청과 분리했어요. 답변을 마치면 서버에 작업을 등록하고, 검토를 통과한 카드부터 보여 줘요. 전체 결과와 기록은 같은 데이터베이스 트랜잭션으로 저장해요. 브라우저 연결이 끊겼다고 생성 작업까지 함께 잃지 않도록 하는 구조예요.

답변을 고쳤는데 예전 결과가 오면?

결과를 기다리는 중에도 답변을 고칠 수 있어요. 그러면 이전 답변으로 시작한 작업이 나중에 끝나는 경우를 처리해야 해요.

설명용 예를 들어 볼게요. 답변 7번 버전으로 카드 생성을 시작했는데, 사용자가 내용을 고쳐 8번 버전이 됐다고 해 봐요. 7번 작업의 모델 응답이 정상이어도 그걸 현재 결과로 저장하면 안 돼요. 사용자가 방금 고친 내용을 반영하지 않은 결과니까요.

이걸 구분하려고 작업에 대화 ID, 소유자, 답변 버전, 실행 토큰을 연결했어요. 답변이 바뀌면 이전 작업을 무효화하고, 새 답변이 결과 생성 가능한 상태가 되면 새 작업을 등록해요. 원문을 큐에 또 복사하지 않고 기존 암호화 저장소에서 읽도록 했고요.

작업을 가져올 때는 PostgreSQL의 FOR UPDATE SKIP LOCKED로 다른 작업자가 이미 처리 중인 항목을 피하게 했어요. 실행 권한에는 만료 시간을 두고 처리 중 갱신해요. 서버가 멈추면 권한이 만료된 작업을 다시 가져올 수 있어요.

저장 직전에도 버전과 실행 토큰, 권한이 유효한지 확인해요. 재시작 뒤 새 작업자가 맡았는데 예전 작업자가 늦게 결과를 보내는 경우까지 구분하려는 거예요. 자세한 흐름은 결과 작업자 코드에 있어요.

입력과 원문도 같이 챙기기

결과 저장 전에는 입력을 잃지 않는 것도 필요해요. 화면에 메시지가 보여도 모델 처리까지 끝난 건 아니니까요. 실패했을 때 같은 답변으로 재시도하고, 화면을 이동했다 돌아와도 작성하던 내용을 이어 볼 수 있도록 초안과 이동 상태를 보존하는 부분을 보완했어요.

추가 질문도 원문과 함께 관리해요. 어떤 문항의 몇 번째 수정본에서 나온 질문인지, 어느 문장을 인용했는지 연결해 두고 현재 답변과 대조해요. 원문을 고치면 그 답변에서 파생된 추가 질문과 답변도 다시 판단하도록 무효화해요.

모델이 만든 질문 속 내용과 사용자가 직접 말한 내용은 구분해서 남겨요. 아직 답하지 않은 문항은 미응답으로, 건너뛴 문항은 건너뛴 상태로 두고요. 빈 부분을 모델이 채워 넣으면 뒤의 카드도 다른 이야기가 될 수 있어서예요. 이 규칙은 개인화 질문 문서에 정리했어요.

확인한 것과 다음에 해볼 것

질문셋을 JSON으로 적어서 앱의 문답과 모델 호출을 재현하는 테스트 실행기도 추가했어요. 앱에서 쓰는 입력 검사와 상태 처리, 모델 연결을 그대로 사용해요. 현재 질문에 맞는 답변이 없으면 임의로 답하지 않고 awaiting_input으로 멈춰요.

11월 18일에는 로컬 12B로 합성 대화의 질문 흐름을 실행했어요. 결과 저장 쪽은 합성 모델 응답과 격리된 PostgreSQL을 연결해 검사했어요. 연결 종료 뒤 완료되는지, 답변 수정으로 이전 작업이 무효화되는지, 실패와 재시작 뒤 복구되는지, 저장한 기록을 다시 읽었을 때 일치하는지를 확인한 범위예요.

다음에는 실제 최종 모델까지 연결해서 질문부터 카드 생성·검토·저장까지 한 대화로 살펴보려고 해요. 필요한 상황을 놓치지 않는지, 같은 내용을 되묻지 않는지, 마지막 결과가 수정한 답변에 맞게 남는지가 궁금한 부분이에요. 기다리는 시간도 질문, 생성, 검토, 저장으로 나눠 기록해 보면 좋겠어요.

기준 코드는 d134a006이며, 검증 범위는 당시 기록을 따랐어요. 실제 31B의 최종 생성·검토 시간과 카드 품질은 추가로 확인할 부분이에요.
