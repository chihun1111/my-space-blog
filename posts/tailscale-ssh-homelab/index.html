Tailscale과 SSH로 홈서버에 접속하기

Chihun2026년 10월 22일5분 읽기

홈서버에서 개발용 VM을 만들 때 SSH 공개키를 먼저 등록하고 Tailscale도 설치했다. 다만 설치 직후부터 Tailscale로 접속할 수 있었던 것은 아니다. 2026년 5월 26일의 최초 구성에서는 Tailscale 1.98.3이 설치돼 있었지만 인증 전이었고, tailscaled도 disabled / inactive 상태였다.

이때는 Ubuntu 24.04.4 VM을 Proxmox의 vmbr0에 연결하고 DHCP로 내부 주소를 받았다. 작업용 Mac의 공개키를 VM 사용자 계정에 등록해 둔 상태에서, Tailscale 로그인은 따로 마무리할 항목으로 남겼다. 패키지가 설치됐다는 것과 그 주소로 실제 접속할 수 있다는 것은 이 과정에서 나뉘었다.

VM으로 바로 들어가는 경로와 호스트를 거치는 경로

5월 27일의 접속 문서에는 두 경로를 남겼다. 하나는 VM의 Tailscale 주소로 바로 접속하는 방식이고, 다른 하나는 Proxmox 호스트를 점프 호스트로 거쳐 VM의 내부 주소에 접속하는 방식이다.

Text
직접 접속
작업용 컴퓨터 → Tailscale → 개발용 VM의 SSH

점프 호스트 경유
작업용 컴퓨터 → Tailscale → Proxmox 호스트 → 개발용 VM의 SSH

접속 명령은 직접 경로의 ssh 사용자@대상주소와 점프 경로의 ssh -J 중간호스트사용자@중간주소 대상사용자@내부주소 형태다. 직접 경로는 VM이 목적지고, 점프 경로는 Proxmox에서 VM까지 이어지는 구간이 하나 더 생긴다.

여기서 사용한 것은 Tailscale 주소를 경유하는 일반 SSH다. 처음 등록한 SSH 공개키와 VM의 SSH 서비스를 사용하는 접속 경로이며, Tailscale SSH 기능의 정책을 별도로 설정하고 시험했다는 기록은 없다.

2026년 10월 22일에는 Tailscale 주소로 Proxmox 호스트와 개발용 VM에 각각 직접 SSH 접속했다. 기존 SSH 인증과 호스트 키만 사용하도록 BatchMode=yes, StrictHostKeyChecking=yes를 적용한 연결이었다. 추가 인증 입력이나 새 호스트 키 등록 없이 접속이 완료됐다. 점프 호스트 경로는 문서에 남아 있지만 이날 별도로 실행 시험하지는 않았다.

접속한 뒤 데몬과 SSH를 각각 확인했다

VM 안에서는 아래 두 명령으로 데몬과 SSH의 상태를 각각 읽었다.

Bash
systemctl is-active tailscaled
systemctl is-active ssh

두 출력은 모두 active였다. 처음 설치했을 때 비활성이던 Tailscale 데몬이 이 시점에는 실행 중이었고, 실제 SSH 연결도 성공한 상태다. 초기 미인증 상태에서 사용한 인증 명령과 적용 시점은 기록에 남아 있지 않다.

이번 접속은 별도 외부 회선이나 다른 장소에서 수행한 시험은 아니다. 여러 VM이 Tailnet에 연결됐던 과거 기록도 있지만, 이 결과로 현재 모든 VM에 접속된다고 볼 수는 없다. 여기서 직접 확인한 것은 Proxmox 호스트와 개발용 VM으로 들어가는 경로다.

접속이 되는 VM과 프로그램이 실행 중인 VM

5월에는 개발용 VM의 에이전트 관련 프로그램과 작업물을 정리하면서 Tailscale과 SSH를 남겼다. 10월에도 이 통로로 들어가 VM 내부 상태를 볼 수 있었다. VM에서 무엇을 실행하는지 바뀌어도 다시 작업할 접속 경로는 유지된 셈이다.

접속 성공 뒤에는 Hermes가 실제로 남아 있는지 따로 살폈다.

Bash
command -v hermes
systemctl --user show hermes-gateway.service \
  -p LoadState -p ActiveState -p UnitFileState

command -v hermes는 실행 경로를 반환하지 않았다. 사용자 서비스는 LoadState=not-found, ActiveState=inactive였고 UnitFileState는 비어 있었다. SSH는 동작하지만 현재 사용자의 PATH에 Hermes 명령이 없고, 해당 gateway 서비스도 등록돼 있지 않은 상태였다.

Tailscale의 연결 진단 문서도 데몬 사이 통신과 호스트의 TCP 연결을 구분한다. 내 환경에서는 데몬 상태, 실제 SSH 연결, VM 안의 프로그램 상태가 각각 다른 답을 줬다. 서버에 들어갈 수 있다는 사실만으로 설치했던 서비스가 지금도 실행 중이라고 판단하지 않게 된 이유다.

개발용 VM의 도구 설치와 메시지 처리 과정은 온라인인 Discord 봇이 답하지 않던 이유에 따로 적었다.
