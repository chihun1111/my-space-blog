NAS부터 시작하도록 둔 VM 부팅 순서

NAS가 먼저 켜지도록 VM 시작 순서를 잡았어요. 자동 시작과 대기 시간, 서비스가 준비되는 시점의 차이를 적었어요.

Chihun2026년 10월 22일수정 2026년 11월 26일5분 읽기

제 홈서버는 NAS를 먼저 시작하도록 순서를 정해 뒀어요. NAS는 order=10, WOL은 40, Home Assistant와 데이터 처리 VM은 50이에요. 다만 순서가 있는 VM이 모두 자동으로 켜지는 것은 아니에요. MinCrafty에는 80이라는 시작 순서가 있지만 자동 시작 옵션은 활성화돼 있지 않아요.

자동 시작 여부와 순서를 따로 저장해요

2026년 10월 22일의 설정이에요. onboot는 호스트 부팅 시 시작 여부를 정하는 옵션이고, startup에는 순서와 대기 시간이 들어 있어요.

VMonboot시작 설정현재 상태
NAS1order=10,up=10실행 중
WOL1order=40,up=30실행 중
Home Assistant1order=50,up=30중지
데이터 처리1order=50,up=30실행 중
n8n1order=70,up=30중지
MinCrafty항목 없음order=80,up=30,down=10중지

LiteKernel·개발용 VM·Linux Mint·Ubuntu 템플릿에는 onboot와 startup이 모두 명시돼 있지 않아요. onboot의 기본값은 0이에요. 따라서 개발 VM이 지금 실행 중이어도 호스트 부팅 때 자동 시작하는 설정이라고 볼 수는 없어요. onboot 옵션

반대 사례도 있어요. Home Assistant와 n8n은 자동 시작이 켜져 있지만 현재는 중지 상태예요. 자동 시작 설정은 다음 호스트 부팅 때의 동작을 정하는 것으로, 현재 전원 상태와는 다른 정보예요.

up은 기다리는 시간이고, 서비스 준비 확인은 아니에요

NAS 설정은 아래처럼 짧아요.

Text
onboot: 1
startup: order=10,up=10

자동 시작 대상 중 낮은 순서값을 가진 NAS가 먼저 시작하고, up=10만큼 다음 VM 시작 전에 기다려요. 그다음은 WOL, 50번 그룹, n8n 순서예요. Home Assistant와 데이터 VM은 같은 50이므로 이 표만으로 두 VM의 선후 관계까지 정하지는 않아요.

up은 시간 지연이에요. NAS의 SMB 공유나 데이터베이스가 준비됐다는 응답을 기다리는 검사는 아니에요. 자동 시작 순서를 구성한 것과 재부팅 뒤 모든 앱의 정상 동작을 시험한 것은 구분해야 해요. VM 시작·종료 순서

MinCrafty의 down=10은 종료 대기 제한이에요. 다음 VM을 시작하기 전 10초를 기다린다는 뜻도, 게임 월드 저장이 끝났다는 보장도 아니에요. 이 VM에는 시작 순서만 남아 있어서 자동 시작 여부를 함께 봐야 해요.

VM 내부의 부팅 대상은 또 다른 순서예요

startup이 VM 사이의 순서를 다룬다면 boot는 VM 안에서 어떤 장치로 부팅할지 정해요.

VMboot 설정
개발용 VM·Ubuntu 템플릿order=scsi0
Home Assistantorder=sata0
LiteKernel·WOL·n8n·데이터·MinCrafty·Linux Mintorder=scsi0;ide2;net0
NAS특정 order 값이 명시돼 있지 않음

그래서 order=50과 order=scsi0는 서로 다른 항목에 속한 값이에요. 전자는 다른 VM과의 시작 순서, 후자는 해당 VM의 부팅 장치예요. NAS의 자동 시작 순서는 분명히 10이지만, 비어 있는 boot 값에서 디스크 우선순위를 추정하지는 않았어요.

게스트 에이전트 옵션도 응답 여부와 구분해요

VM 열 개에는 QEMU 게스트 에이전트 사용 옵션이 agent: 1 또는 agent: enabled=1로 들어 있어요. 하지만 데이터 처리 VM에서 게스트 명령을 조회했을 때는 아래 오류가 돌아왔어요.

Text
QEMU guest agent is not running

같은 호스트의 NAS에서는 게스트 에이전트를 통해 OS 정보와 앱 상태를 읽을 수 있었어요. 옵션이 켜졌다는 사실만으로 게스트 안의 에이전트가 모두 응답하는 것은 아니었어요. 데이터 처리 VM도 전원은 켜져 있었으므로, 전원·에이전트·앱 상태를 각각 봐야 했어요.
