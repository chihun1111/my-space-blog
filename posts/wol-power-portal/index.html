WOL 포털로 PC를 켜고 Windows·Ubuntu 부팅까지 연결하기

매직 패킷 재전송부터 Windows 준비 확인과 일회성 Ubuntu 부팅까지 전원 포털을 고친 과정이다.

목차

  • Windows가 준비된 뒤에 Ubuntu 부팅을 요청했다
  • 오래 걸리는 부팅을 별도 작업으로 관리했다
  • 현재 OS에 맞게 종료·재부팅 명령을 나눴다
  • PowerShell에서 끝난 명령의 결과를 호출자에게 전달했다
  • Tailscale 뒤에서 포털과 전원 명령을 연결했다

홈서버에 WOL용 VM을 두고 웹에서 PC를 켜는 포털을 만들었다. 대상 목록과 상태 확인, 종료와 재부팅을 붙였고, Windows와 Ubuntu를 함께 쓰는 PC를 위해 다음 한 번만 Ubuntu로 부팅하는 작업도 연결했다.

패킷을 보낼 주소, PC가 준비됐다고 판단할 시점, 현재 실행 중인 OS를 각각 처리해야 했다. 2026년 8월에는 브로드캐스트와 패킷 반복 전송을 손봤다. 10월에는 OS별 전원 명령을 나누고 Windows 스크립트의 종료 코드 전달을 수정했다.

실제 PC에서 전원 동작과 OS 전환이 성공했는지는 실행 로그가 남아 있지 않아 확인하지 못했다.

WOL을 담당하는 VM과 웹 포털

WOL용 VM은 Proxmox에서 별도로 관리한다. 2026년 10월 22일에는 실행 중이었고, 설정은 다음과 같았다.

항목설정
CPU1소켓 · 2코어, host
메모리4096MiB, 즉 4GiB
시스템 디스크local-lvm의 scsi0, 35G
머신·펌웨어q35 · OVMF
SCSI 컨트롤러virtio-scsi-single
네트워크VirtIO NIC → vmbr0
자동 시작onboot=1, order=40,up=30

웹 화면은 Next.js로 만들고 정적 번들을 FastAPI에서 제공하도록 구성했다. 화면과 API가 같은 오리진에 있으므로 프런트엔드에서는 /api/... 상대경로로 요청한다. 대상 PC 목록, 상태, Wake·종료·재부팅 버튼, Ubuntu 부팅 작업과 최근 로그가 이 화면에 있다.

대상 정보는 JSON 파일로 관리한다. 이름, 주소, MAC 주소와 전원 명령을 연결하는 구조다. MAC 주소가 없을 때는 대상이 온라인인 상태에서 ARP 정보를 이용해 찾는 처리도 넣었다. 주소를 등록한 것과 WOL을 보낼 MAC 주소까지 준비된 것은 구분한다.

현재 저장소의 운영 구성은 Docker Compose를 기준으로 한다. 이전 systemd 파일과 설치 스크립트도 남아 있지만 호환용이다. 두 방식을 함께 띄우는 구성으로 안내하지 않고 실행 주체를 하나로 정리했다.

브로드캐스트 주소를 맞추고 전송 결과에 남겼다

8월 26일에는 WOL이 사용할 인터페이스와 브로드캐스트 설정을 당시 LAN에 맞게 수정했다. 매직 패킷을 만드는 코드와 패킷을 내보낼 네트워크 설정을 함께 맞추는 작업이었다.

기본 구현은 Python 소켓을 사용한다. 브로드캐스트 전송을 허용한 UDP 소켓을 만들고, 대상 MAC 주소로 구성한 매직 패킷을 9번 포트로 보낸다. 별도로 etherwake를 사용하는 분기도 있다. Python 방식에서는 브로드캐스트 목적지, etherwake 방식에서는 사용할 인터페이스가 전송 경로를 설명하는 값이다.

설정을 고치면서 API 응답과 로그에도 전송 방식과 목적지를 남겼다. 요청이 끝났다는 사실과 함께 서버가 어떤 설정으로 패킷을 보냈는지 되짚을 수 있게 했다. Ubuntu 부팅 작업 안에서 WOL을 보낼 때도 같은 정보를 기록하도록 연결했다.

이 로그의 전송 성공은 PC 부팅 완료와 다르다. 소켓이 패킷을 보낸 다음에는 대상이 실제로 준비됐는지 따로 기다려야 한다. 이후 선택 부팅 작업을 붙일 때도 이 구분을 유지했다.

한 번 보내던 매직 패킷에 반복 전송을 붙였다

8월 27일에는 전송 횟수와 간격을 설정으로 분리했다. 한 번만 전송하던 코드를 바꾸고 기본값을 다섯 번, 0.25초로 두었다.

Text
WOL_PACKET_COUNT=5
WOL_PACKET_INTERVAL=0.25

이 값은 저장소의 기본값이다. 실행 환경에서 다른 값을 지정할 수 있으므로 모든 운영 요청이 반드시 이 횟수로 나갔다는 뜻은 아니다.

같은 소켓에서 지정한 횟수만큼 보내고 전송 사이에 간격을 두는 방식으로 구현했다. 전송 횟수는 최소 한 번, 간격은 0 이상으로 처리한다. 응답과 동작 로그에는 packet_count를 추가했다.

테스트 코드에는 다섯 번 전송하고 네 번 기다리는 경우를 넣었다. 각 패킷의 목적지 포트가 UDP 9인지도 검사한다. 이 테스트가 확인하는 것은 반복 전송 로직이다. 실제 PC의 부팅 시간이나 성공률을 잰 결과와는 다르다.

Windows가 준비된 뒤에 Ubuntu 부팅을 요청했다

선택 부팅은 일반 Wake보다 단계가 많다. PC가 꺼져 있다면 먼저 켜고, Windows가 준비된 다음 다음 한 번의 부팅 대상을 Ubuntu로 지정해야 한다. 재부팅 요청 뒤에는 Ubuntu가 올라왔는지도 확인한다.

Text
현재 OS 확인
  ├─ Ubuntu 준비 완료 → 작업 완료
  └─ Windows 미준비 → WOL 전송 → Windows 준비 대기

Windows SSH 준비 확인
  → 다음 한 번의 Ubuntu 부팅 설정
  → 재부팅
  → Ubuntu SSH 준비 확인
  → 작업 완료

8월 26일에는 windows_login_ready 단계를 추가했다. Windows의 제한 SSH 명령에서 정확한 준비 응답을 받아야 다음 단계로 넘어가도록 바꿨다. ping 응답이나 열린 SSH 포트만으로 Windows 로그인이 준비됐다고 판단하지 않는다.

같은 PC의 네트워크 응답만으로는 현재 OS까지 알 수 없기 때문이다. Windows는 전용 준비 명령의 응답을 보고, Ubuntu는 별도의 SSH 경로에서 uname -s의 Linux 응답을 확인한다. SSH 명령이 정상 종료되고 출력이 예상한 값과 정확히 일치해야 준비 상태로 처리한다.

다음 부팅 대상을 지정하는 BootNext 설정에 실패하면 재부팅을 진행하지 않는다. 앞 단계가 실패했는데 재부팅만 해 버리는 상황을 막는 조건이다. Ubuntu가 이미 준비된 경우에는 추가 WOL이나 재부팅 없이 작업을 완료한다.

오래 걸리는 부팅을 별도 작업으로 관리했다

Ubuntu 부팅 요청은 API가 작업을 만들고 202 응답을 반환하는 방식이다. 화면은 작업 ID로 상태를 조회한다. 작업 상태는 SQLite에 저장하고 진행 단계와 종료 결과를 구분한다.

기다리는 시간도 구간별로 나눴다. 아래 값은 현재 저장소의 기본값이며, 실제 부팅 시간이나 운영 환경의 재정의 값을 측정한 표는 아니다.

구간기본값
Windows 준비 대기180초
Ubuntu 준비 대기300초
전체 부팅 작업480초
상태 확인 간격5초
개별 SSH 명령 제한10초
재부팅 시작 대기30초

단계별 제한과 전체 제한을 함께 사용하므로 앞 단계가 늦어졌다고 작업이 무한히 늘어나지는 않는다. 같은 대상에 활성 작업이 있으면 중복 요청을 막고, 취소는 BootNext를 설정하기 전까지만 허용한다. 다음 부팅 대상을 바꾼 뒤에는 화면의 작업 취소만으로 원래 상태로 돌아가는 것이 아니기 때문이다.

재부팅 응답이 불분명하면 바로 성공으로 처리하지 않고 두 OS의 상태를 다시 살핀다. Windows가 계속 살아 있고 재부팅이 시작되지 않은 경우에는 일회성 설정을 정리하는 경로도 있다.

서비스 재시작으로 중단된 작업은 자동으로 이어서 실행하지 않고 실패 상태로 정리한다. 포털이 다시 켜졌다는 이유만으로 예전 전원 명령이 뒤늦게 나가지 않도록 한 처리다.

현재 OS에 맞게 종료·재부팅 명령을 나눴다

10월 6일에는 종료와 재부팅 경로를 수정했다. Ubuntu 선택 부팅을 활성화한 대상으로 지정한 PC에서는 현재 OS에 맞춰 명령을 고르도록 했다. 이 경로는 UBUNTU_BOOT_ENABLED=true이고 요청 대상이 UBUNTU_BOOT_TARGET과 일치할 때만 사용한다. 활성화 옵션의 코드 기본값은 false이며, 다른 대상은 대상 목록에 등록한 기존 명령을 사용한다.

수정한 코드는 두 OS의 준비 상태를 SSH로 확인하고, 확인된 OS의 명령만 실행한다. 어느 쪽도 확인할 수 없으면 503으로 끝낸다. 한 OS의 명령이 실패했다고 다른 OS 명령을 추측해서 보내지 않는다.

전원 요청은 명령이 정상 종료되고 종료 또는 재부팅을 받아들였다는 정확한 응답이 돌아와야 접수 성공으로 처리한다. 이 응답 역시 실제 종료·재부팅의 완료를 뜻하지는 않는다.

이 대상의 일반 재부팅과 Ubuntu 선택 부팅은 목적지도 나눴다. 일반 재부팅 버튼은 Windows를 다음 부팅 대상으로 지정한 뒤 재부팅한다. Ubuntu로 켜는 기능은 앞에서 설명한 별도 작업을 사용한다. 같은 PC의 재부팅이어도 다음 OS가 다르므로 명령과 처리 흐름을 구분했다.

PowerShell에서 끝난 명령의 결과를 호출자에게 전달했다

같은 날 저장소의 Windows 스크립트 연결 예제도 한 번 더 수정했다. 기존 예제의 호출 방식에서는 전원 동작을 처리한 뒤에도 호출자 쪽의 미지원 명령 분기로 흘러갈 수 있었다.

처리 스크립트를 dot-source하는 방식 대신 호출 연산자로 실행하고, 곧바로 exit $LASTEXITCODE로 종료 코드를 전달하도록 README의 래퍼 예제와 스크립트 주석을 바꿨다. 정상 처리 뒤에 래퍼의 나머지 분기가 실행되지 않도록 하는 연결 방식이다.

원격 명령이 접수됐더라도 호출자가 뒤에서 오류를 내면 웹에서는 실패로 읽을 수 있다. 실제 처리 결과와 API가 받아 보는 결과를 맞추기 위한 수정이며, Windows 처리 스크립트의 모의 검사 파일도 함께 추가했다. 이 변경 기록은 연결 예제와 검사 코드에 대한 것이고 실기기 래퍼의 배포·검증 결과까지 남아 있는 것은 아니다.

Tailscale 뒤에서 포털과 전원 명령을 연결했다

저장소의 운영 구성은 Tailscale Serve를 앞에 두고 FastAPI를 localhost의 8000번 포트에 연결한다. Docker는 WOL 브로드캐스트를 보낼 수 있도록 호스트 네트워크를 사용하되 웹 서버의 바인딩은 localhost로 제한했다.

API는 사용자 식별 헤더가 없으면 401로 처리한다. 현재 코드의 이 검사는 사용자별로 서로 다른 전원 권한을 나누는 기능은 아니다. 식별 헤더가 있는 요청을 받는 구조이므로 실제 접근 범위는 Tailscale의 접근 정책과 장비 공유 설정도 함께 결정한다.

컨테이너의 기본 파일시스템과 SSH 설정은 읽기 전용으로 연결하고, 대상 목록·로그·부팅 작업 DB처럼 변경이 필요한 데이터는 따로 유지한다. 전원 버튼을 누른 요청이 어떤 대상과 명령으로 이어졌는지 남기는 구성이다.

VM의 전원은 켜져 있었지만 게스트 에이전트는 응답하지 않았다. 포털의 정상 응답 여부는 확인하지 못했다. 저장소에는 실기기 검사 스크립트가 남아 있다.
